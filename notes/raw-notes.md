## Ch1 What Is Observability? (read in full; 6 figures viewed)
**Argument:** Observability is a property of software dependability (like reliability), measured qualitatively on a spectrum, not a tool category. Two incompatible telemetry models: three pillars (fine for infra/3rd-party code) vs unified wide-event storage (right for code you write). AI/agents make it the last line of defence for validating developer intent.

- Term coined by **Rudolf E. Kálmán, 1960** ("On the General Theory of Control Systems"), birth of modern control theory. Observability and controllability are **duals**. Observable = can infer full internal state from measured outputs. If info never captured, no engineering recovers it. Software has no equivalent of controllability.
- 1st edition defined observability as a new breed of tooling → disfavoured: emphasised features, people care about outcomes. 2e: property of systems.
- **Dependability** = "trustworthiness of a computer system"; not numerically scored. Nines measure availability but "nines don't matter if users aren't happy".
- **Jean-Claude Laprie, 1995**: six properties: Availability (deliver when requested), Reliability (deliver as specified), Maintainability (repair/evolve), Safety (no catastrophic consequences), Confidentiality (no unauthorised disclosure), Integrity (no improper alteration). Assess functions (should do), behaviour (does), structure (how built), incl. environment and people → systems are **sociotechnical**.
- Authors add 7th: **Observability = ability to understand or debug any given system state.**
- Monolith era: failures mostly binary up/down (+ rare "inexplicably slow"). Cloud era: zoo of partial failures; slowness with no smoking gun is now the most common failure mode. Examples: partially degraded LB, hardcoded us-east-1 config from containers in India, dependency on another team's infra behind an API.
- Monitoring tells you up/down and (if sophisticated) where slow, not **why**. Need detect, where, why.
- Qualitative assessment: **fault detection** (know before customers? support spike but dashboards green = detection problem), **triage** (alert storms in low-observability systems), **understanding why** (hardest; meta-process of encoding breadcrumbs instead of senior-engineer intuition). Scotty "feel of the deck plates" analogy. Key test: can any engineer regardless of experience diagnose novel issues by interrogating data?
- **Cardinality** sidebar: number of unique values in a column (bool=2, UUID=max). Useful attributes are high-card: build number, commit hash, container ID, span ID, user ID, app name, query hash. Downsampling (e.g. 5xx bucketing) can't be undone. A single metric can add tens of thousands of dollars/week if cardinality slips in.
- High-observability capabilities: understand novel states without shipping new code; compare flag sets and group by endpoint/API key/query hash with no cardinality limits; see user interaction by request/browser session/mobile session/chat history; select SLO-violating events and surface patterns (example: slow requests from AU read replicas, build at 1% canaries with flags x,y,z, DNS timeouts); find outliers easily. Needs precision, flexibility, speed.
- **Three pillars** (metrics→TSDB, logs→log aggregator, traces→tracing service; Fig 1-1 three cylinders). "Polite fiction": also errors, exceptions, profiles, product analytics, security events each in silos. Example request `GET /api/checkout trace_id=7f3a9c user_id=u_8821 200 OK 142ms`.
  - Fig 1-2 metrics: aggregates across all requests, not this one (http_requests_total 48,291; p50 98ms; p99 380ms; error rate 0.3%; db p50 61ms).
  - Fig 1-3 logs: 5 timestamped lines (incoming request, auth token verified, db query rows=4 89ms, cache miss, request complete 200 142ms 4210 bytes).
  - Fig 1-4 trace waterfall: GET /api/checkout 142ms; auth.verify_token 12ms; db.query_cart 89ms (db.connect 10ms, db.execute 79ms); cache.get_pricing 13ms; render.checkout_page 23ms.
- Infra emits whatever third-party code emits; storing logs and metrics cheaply is still right for infra. For code you write you control emission → instrument deliberately. "Metrics and logs made sense for the router… mismatch for the billing service."
- Telemetry decisions are **product decisions not infrastructure decisions**; most teams make them by default not design.
- Terminology: "traditional/legacy observability", "three/multiple pillars model" vs "modern observability"/"unified model". They tried "observability 1.0 / 2.0" and dropped it (footnote).
- **Unified storage model** (Fig 1-5: one columnar DB of wide structured canonical log events or traces; Fig 1-6: one JSON wide event for the checkout with when/request/user/app context (feature_flag.new_checkout, cart.item_count, cart.total_usd, cache.hit)/where time went (db.query_duration_ms 89, auth 12, render 23)/deployment (service.name checkout-api, deploy.build_id, trace.trace_id, span_id)).
- Six principles (named): (1) data valued by context, increases combinatorially not linearly (= **high dimensionality**); (2) details are the most identifying part of any dataset (**high cardinality is a superpower**); (3) **pre-aggregation is a one-way trip**; (4) you don't know what you don't know (store raw, aggregate at query time; write-time schemas/indexes/aggregates create dead ends); (5) static dashboards have limited value ("static dashboard is a stock phrase; dynamic interface is a conversation"); (6) fast feedback loops are everything (minute-long queries = filing tickets, not exploring).
- BI tools (columnar stores, high-card, interactive) have done this for 20+ years: funnels, cohorts over billions of events.
- **Dimensionality** sidebar: number of unique fields. 4 fields → 6 pairwise, 15 combinations; 8 → 28 pairwise, 255; 30 → 435 pairwise, ~1.1 billion combinations. Footnote: adding a 30th attribute to a 29-attribute event adds as much value as all preceding 29 combined (2^n doubling).
- The two models are incompatible: can't store data in one place and three places.
- **Observability is the validation of developer intent.** When agents write/test/review/ship faster than people, verification becomes the bottleneck; telemetry is the last line of defence. "Only production is production." AI makes nondeterminism a feature.
- Agents in production: investigations non-deterministic; senior engineers' tacit checks (latency by build ID after risky deploy, cache behaviour after schema migration, N+1 when billing slows) must be encoded in the system. Agents need context, relationships, diverse sources, semantic conventions (ontological grounding), precision. Three pillars require intuitive leaps between pillars; unified data doesn't.
- Guardrails: feature flags, progressive delivery, canaries, SLOs, characterization tests, automated rollbacks. AI is both enabler (auto-instrumentation, anomaly detection) and forcing function. "Handcrafted artisanal code → software factory".
- Conclusion: AI SRE/agentic hopes uncertain; "track record with magic is not outstanding".
- Interview angles: define observability vs monitoring; cardinality vs dimensionality; why pre-aggregation is lossy; when three pillars is still right (infra, 3rd party); unified model; Laprie + 7th property; three questions detect/where/why.

## Ch2 How Code Crosses Over: Validating Developer Intent in Production (read in full; no figures)
**Argument:** Deploys aren't a binary dev→ops switch; they're a process of building confidence. A flywheel of six practices (0–5) validates developer intent in production, and all depend on Practice 0: rich, high-cardinality observability. Teams that tried flags/canaries on three-pillars data got mediocre results.

- Good software = fulfils its purpose, for as long as needed, as efficiently as possible. Always ask "for what purpose? under which constraints?" Practices are rarely good/bad (code review, devs on call → "it depends").
- Cost of software = cost of maintaining it. Readability was a proxy when human cognition gated every change.
- **Durable vs disposable code** (distinction is the maintenance/change model, not AI vs human):
  - Durable: mutate in place via small diffs to a baseline assumed good; intent/user expectations/dependency commitments are bound up in code; "no test lets me trust new code more than code already running in prod". User expectations have a small "change budget". Maintenance is expensive, gated on understanding.
  - Disposable: regenerate instead of maintain (add a sentence to the spec; generate 10,000 variants). YOLO fine for prototypes; migrations/upgrades are great disposable use cases but need tests.
  - Immutable infrastructure analogy: we regenerate infra because we understand it; "regeneration is proof". Shift to durable systems with regenerable code is coming (ch32).
  - Maintenance horizon not knowable up front; "quick hack becomes load-bearing". When disposable graduates to durable: tests, review, always instrumentation, SLO coverage if needed.
- Production quality = dependability; code in prod accrues commitments/expectations.
- **Critical path**: write it down, check team/adjacent teams agree. "What happens if this breaks?" (NYT headline; $20M per minute of HFT delay; someone could die). Compass: **frequency, criticality, visibility, blast radius**. Scaffolding (rare/invisible/low impact) vs **post office** (rare+invisible but core: payroll, security) vs **cathedral** (constant, carries business, users sensitive). Caveat: anything whose blast radius can take down critical code is critical (rogue cron job). Use isolation/modularisation. Audit critical path periodically.
- Rule of thumb: the closer to persisting data (DBs, OS, filesystems, medical devices), the more cautious; persistence mistakes can be permanent (can't un-corrupt a table). Use AI there with more human understanding, conservative staging, more observability before/during/after.
- Crossover dev→prod should be boring (footnote: harder crossovers are prod→prod under load).
- **Practice 0: rich data + precision tooling** (keystone species; see ch24/25). Flags need slicing by arbitrary flag subsets; canaries need canary vs baseline comparison; automated rollbacks need precise trustworthy signals. Requires columnar store, read-time aggregation, arbitrary subset comparison, high cardinality.
  - Alternatives if stuck: local agentic dev → stash traces in **DuckDB** or **Apache Iceberg**. If locked into a three-pillars vendor contract: **standardise on logs or traces, not both**. Logs if tracing isn't a top pain (canonical logs, one wide event per unit of work/service hop, propagate context); traces if it is, loaded with context.
- **Practice 1: dev↔prod feedback loop**: instrument as you write; get to prod immediately; autodeploy from CI/CD; look at your change through your instrumentation; "is it doing what I thought? anything weird?" Gold standard: "look at it before you forget what you were trying to do". "99.99% before and after deploy tells you nothing"; aggregates conceal sins. AI + **MCP** (Model Context Protocol) bring telemetry to IDE/Slack. Development doesn't end at merge.
- **Practice 2: test before deploy.** Purpose of tests: prevent known classes of problems recurring + give confidence to begin validating in prod (narrower than "correctness"). Unit (complex logic), **contract** (across team/org/3rd-party boundaries), integration (seams, implicit contracts), E2E (less useful, flaky; SLOs are the operational version). AI writing tests for its own code repeats its assumptions: do tests validate intent or implementation? Bar: "the mistakes you find in prod will be new mistakes". Predict shift to property-based, behavioural, **characterization tests** (stability/continuity of expectations).
- **Practice 3: instrument and validate in prod.** "Everyone tests in production" (even with 24h traffic replay on a replica, every deploy is unique). Code ≠ system; system = code+infra+users+builders+operators+data over time. Instrumentation = endoscopy (inside-out) vs infra logs/metrics scanning from outside. Tips: put source line number in span attribute; put line number in SQL query comment and the comment as attribute; store query fingerprints/normalized queries. OTel + LLMs: now easier to write code with instrumentation than without. Instrumentation in prod = "the living spec".
- **Practice 4: decouple deploys from releases with feature flags.** Deploy = build/test/roll out (engineering); release = meaningfully change user experience (product/marketing). Flags can be a 2-column DB table. Autodeploy each artifact at least to canary/internal prod; one changeset per deploy → ownership, notify dev. Batching 20 people's changes → 20x likely to break and all roll back. Merge = deploy (atomic; don't merge if you don't want it out). Releases: flip a flag at exactly 10:00:00. Advanced: internal users, opt-in, segments by region/plan/language, 1% of Brazilian users, randomized per time zone, instant kill switch. Flags + observability > sum of parts.
- **Practice 5: progressive delivery, canaries, automated rollbacks.** Blue-green (copy + flip at LB, drain old), canary (single node/small slice then all), rolling (replace instances one/few at a time; chapter assumes rolling). Facebook early 2010s: week-long rollout, hundreds of diffs in flight, sandboxes → intern.facebook.com bake for a week → 1% of one country → dial up → other regions; health checks at each step, auto-revert to developer.
  - Failure story: 1% canary dashboards looked fine; at 70% every request queued on the same DB row lock. Canary failure causes: errors too small for noise, threshold effects, sample bias, aggregates smoothing outliers, cascading failures, thundering herds/retries, upstream/downstream contention, unrepresentative sample, problems not in watched metrics (data corruption).
  - Two fixes: (1) "make new mistakes": wrap each failure into automated health checks, never fail same way twice; (2) validate developer intent with precise cohort comparison: new vs old build, one endpoint, by user tier → detect "40% slower for enterprise plan on billing endpoint" at 1% traffic. Agents don't mind checking after every deploy. Rollback only as trustworthy as its signal → back to practice 0.
- Bonus: **capture/replay** (DB snapshot + 24h prod queries replayed under different versions/hardware/concurrency/speed, reset between runs; gold standard for DB upgrades); **traffic splitter** (fork request to old+new API, diff responses, return old, log differences; writes need a DB replica behind new API); **strangler fig** (Martin Fowler; transitional architecture, interfaces, dual write, backfill, switch reads, deprecate).
- Observability = "feedback loop of feedback loops"; sense-making apparatus of production.
- Immutable infra taught "mutability is the enemy of understanding". Honeycomb sticker: "Undeployed code ages like fine milk."
- Conclusion: practices aren't new; weak signal made them mediocre; AI lowered cost; "can't automate rollbacks on signals you don't trust".
- Interview angles: deploy vs release; canary failure modes and how to detect a 1% regression; durable vs disposable; critical path compass; test-in-prod defence; why one change per deploy.

## Ch3 The Origins of Observability in Software (read in full; Charity Majors' voice; no figures)
**Argument:** Observability was meant to be a developer tool for understanding code in prod (unknown-unknowns), with a technical definition and six functional requirements. Vendors rebranded monitoring as observability (2019–21), so the term lost meaning. Cost and AI are pushing the industry toward the unified model.

- Charity: cofounder/CTO Honeycomb; ops/SRE/DBRE at Linden Lab, Parse, Facebook. Christine Yen cofounder (analytics background). "Rage-driven development".
- Genealogy footnote: **Bryan Cantrill**, deck "Software Observability" (2003) to keep Sun funding **DTrace**; then Twitter's "Observability Engineering" team (early 2010s).
- Pre-Honeycomb tool limits: strict cardinality caps for cost, minute-long queries, manual correlation.
- Ops department 20 years ago owned everything (DNS/BIND, LDAP, Kerberos, datacenters...). Cloud wave from **2006** (Google hosted email; AWS S3 and EC2). Over ~15 years each ops skill replaced by managed API/SaaS/PaaS. Except monitoring, which returned as "observability" and now is **20–30% of all infrastructure spending at many companies**.
- **Honeycomb founded 2016.** Definition: "ability to understand whatever is happening in your system, at any time, even if you've never encountered this system state before"; needs high cardinality, high dimensionality, explorable interface, visualize events over time as a trace. Observability (devs, code in prod) and monitoring (ops, infra) complementary, need both.
- Timeline: traction 2017, buzzy 2018; Monitorama renamed "Monitorama (+ Observability)"; vendors rebranded **2019–2021**; **Gartner added "observability" category in 2022** → term meaningless.
- Complexity: 2010 LAMP stack (Linux, Apache, MySQL, PHP) suited monitoring. 2026: no typical stack; services, models, platforms, APIs, agents, nondeterminism.
- **Finance analogy**: personal bank account (direct deposit, autopay, check balance) = monitoring; running a bank (trace every transaction across millions of accounts, interest, depreciation, tax, fraud/compliance alerts, jail if wrong) = observability. Observability costs more because it does more; once needed, going without is more expensive.
- **Scuba** at Facebook (used while at Parse): novel problems findable without prior knowledge; investigations fast and cheap; **junior engineers out-debugged experts**; categories of problems became support tasks. Had the Scuba whitepaper; told it was a "solved problem".
- Control theory definition: "a measure of how well internal states of a system can be inferred from knowledge of its external outputs." Existing tools required knowing internal state to find it (circular dependency); observability breaks it.
- **Six functional requirements**: (1) high-dimensionality: wide structured events per unit of work, ideally hundreds of attributes; (2) high cardinality, yes to unique IDs; (3) store raw, aggregate at read time, flexible inferred schemas/indexes, every key fast; (4) zoom from single request to whole system; visualize as trace; (5) exploratory UI not static dashboards; (6) queries in seconds.
- Traditional tools good at **known-unknowns**; modern observability → **unknown-unknowns**; product quality, each user's experience, being surprised by users.
- Every observability startup since 2019 follows recipe: wide structured events + columnar store. Then no public columnar engines (Honeycomb wrote its own); now DuckDB, ClickHouse, Snowflake.
- 2024: **Observability 1.0** (signal per tool; correlations predefined/maintained by hand; pay to store many times) vs **2.0** (one unified store; rich structured data; pay once; trace or slice-and-dice; no dead ends). Early 2026: Hazel Weakly proposed **lakehouse = "observability 3.0"**; a "4.0" exists too. Charity mostly stopped using numbering (vendors angry; not less advanced, different use case).
- Charity's personal opinion: world moving to unified model. **Gartner: 10–20 observability tools is the norm → 10–20x cost per request at minimum.** Losers when monitoring/observability blurred: developers and finance (pay to store same data repeatedly, plus bridging data).
- AI attacks status quo: technical enabler; fresh ecosystem; competitive forcing function for reliability/guardrails; agents are gluttons for context; nondeterminism → must instrument agents; **bottleneck moved from writing code to understanding it**.
- Business side went through this 20 years ago with columnar engines (analysts: from predefined metrics to slice-and-dice). Gap between observability cost and value = mismatch of tool to use.
- Fast feedback loops = cornerstone of high-performing orgs; compounding flywheel (ch24–25). Leaders learning AI investment pays off only after investing in reliability and observability. Every company needs someone/team who understands observability + systems thinking. "Attention is the scarcest resource."
- Interview angles: monitoring vs observability (known vs unknown unknowns; finance analogy); six requirements; why the term lost meaning; observability 1.0/2.0/3.0; cost multiplier argument.

## Ch4 Getting Started with Instrumentation (read in full; no figures)
**Argument:** Instrumentation is the cornerstone of observability. Use OTel, combine auto + custom instrumentation, let the code authors own it, build a strategy around critical user journeys and domain errors, defer processing decisions downstream, and understand cost levers, especially sampling (head vs tail).

- Instrumentation = adding code so apps emit data about runtime behaviour. Analogy: city lights from a plane; city planners need traffic sensors/meters.
- Without it: add log lines after problems, wait for repro, educated guesses.
- Vocabulary: **logs** = discrete events at points in time (unstructured → structured key-value); **metrics** = numeric measurements over time (counter, histogram); aggregation makes them cheap but loses drill-down context; **traces** = journey of one transaction across services, made of **spans** (example: order → inventory, shipping, payment, email receipt).
- **OpenTelemetry**: vendor-neutral APIs, libraries, tools; "universal translator". Separation of concerns: API in code, destination configurable; send to multiple backends simultaneously; swap backend via config only. **API is no-op by default** → library authors can call it with no overhead unless configured. Auto-instrumentation for HTTP, DB, external calls with few lines.
- **Auto vs custom: use both.** Auto = breadth, intercepts frameworks/libraries, lowest common denominator ("skeleton"). Custom = business logic ("muscles"); e.g. auto says DB query took 200ms; custom says it was part of a registration flow that failed due to duplicate email. Auto-instrumentation can be overwhelming in prod: know what to take away (every DB/Redis call spans may hurt performance in prod).
- **Ownership**: shift from ops adding monitoring after deploy to developers owning instrumentation as part of design. Org enablers: standard libraries, code review guidelines, docs (Part VI). Instrumentation evolves; treat as a primary deliverable like tests (ch9 ODD). Discuss telemetry in feature planning, check in code review, find telemetry gaps in post-incident reviews.
- **Custom instrumentation strategy**: start from **critical user journeys** (ch11): ecommerce = registration, search, cart, checkout; CMS = create, publish, consume. Capture domain errors ("insufficient inventory", "invalid coupon code", "user not in correct experiment group"); distinguish temporary vs permanent and actionable vs not. Questions: which users affected? key pipeline stages? which feature flags? Capture **why** context: user segments, active flags, request source. Conventions: standard attributes, naming, templates for background jobs/API endpoints (ch31).
- Don't capture everything blindly: TSDBs break on high-cardinality metrics; full-text search DBs need indexing/precomputed schemas; noise and cost.
- **Processing/pipelines**: drop/transform, convert formats, normalise, filter PII (ch16). Instrument backend-agnostic, **defer processing decisions** later in the pipeline: easier to remove data than to wish you'd collected it. Consider scaling (not every user needs global replication / sub-ms RPC) → **telemetry layering** (ch7).
- **Costs**: visible (storage, memory, compute; vendor bill or infra+labour for build, ch29) and hidden (data across 10–15 tools → cognitive overload, slower incident resolution; cost-management overhead such as working out why spans were sampled or cardinality workarounds; **network egress** between AZs/regions/clusters for self-hosted). Pipelines can buffer high-res locally and ship aggregates.
- **Sampling**: best practice to sample all telemetry at any scale. Two ways: before or after emission.
  - Before: **metrics are a form of sampling** (pre-aggregation discards events). **Probability-based head sampling**: keep x%. Fine at very high volume; at 1% sampling an error occurring 0.1% of the time is likely missed entirely. Head decisions can't know downstream outcome (errors). Trades debuggability for cost.
  - After: **tail-based sampling** buffers all spans of a trace and decides on the whole (is it another boring 200 OK, or interesting?). Optimises fidelity. Details ch15.
- Interview angles: auto vs custom instrumentation; who owns instrumentation; head vs tail sampling trade-offs (0.1% error at 1% sample); hidden costs; OTel no-op API; defer processing.

## Ch5 Structured Events Are the Building Blocks of Observability (read in full; figs 5-1,5-2,5-3,5-5 viewed; 5-4 is A→B→C parent-child per text)
**Argument:** Metrics, logs and traces aren't inherently different data types. All can be expressed as structured events; capture one context-rich wide event per unit of work and derive metric/log/trace views on demand. "The shape of the data you collect constrains the questions you can ask later. When you pre-decide the shape, you pre-decide the investigation."

- Guest contributor Jeremy Morrell is primary contributor.
- **Event** = any data emitted; practically, a record of everything that occurred during a **unit of work**. **Structured event** = parsable into key-value pairs; think flat JSON object; maps to a DB row with columns.
- **Metrics**: born 1988 with **SNMPv1 (RFC 1157)**. Single number + optional tags; disposable, cheap, predictable footprint, easy to aggregate in regular buckets (e.g. every 60s). Optimise for volume/resources (1980s constraints). Fields: timestamp (rounded to interval, 6:16:23→6:16:00), name (http.request.count, cpu.utilization), measurement, **type** (how to combine), attributes/tags. OTel models "metric events" on the wire similarly.
  - Aggregation: records with same name+attributes+interval combine. **Counter** (Fig 5-1: 112 + 78 = 190). **Gauge** (Fig 5-2: cpu_temp 80.1 then 83.8 → keep last = 83.8; e.g. 10-second sensor → 6 readings/min, keep last).
  - **Average of averages pitfall**: per-instance averages 120, 230, 200 ms → naive mean 183ms is wrong. With counts 100/57/98 and totals 12,000/13,110/19,600 ms → correct overall average **175 ms** (44,710/255). Histogram type captures count+sum. If you didn't set it up beforehand, the answer is gone forever.
  - Metrics skew to cost reduction at expense of debuggability; right trade-off when storage/egress were expensive.
- **Logs**: unstructured text for humans; one event split over multiple lines (accepted connection, basic auth for user foo, processing /super/slow/path, 200, closed connection). Querying unique users needs regex (`regexp_extract`), costly even with full-text index. Centralised aggregators; parsers struggle with inconsistent formats.
  - Structured logs (JSON key-value) → sparse table; query becomes `SELECT DISTINCT user ... WHERE message='basic authentication accepted'`.
  - **Structured log vs structured event: no difference**, except whether datastore treats them as structured data or strings.
  - Add a **request_id** to each line (7kX9m) → `SELECT * WHERE request_id='7kX9m'`. Simple model of tracing: "events that share the same ID".
- **Tracing** demystified: "fancy logs" + "context propagation" ("passing some IDs around"). Vendors present SDKs as magic. Distributed tracing tracks a request across process/machine/network boundaries; helps with interdependencies (DB latency stacks up 3–4 layers upstream, seen in dozens of services). Works in single processes too.
  - Waterfall (Fig 5-3: service "saas-update" spans start, UpdateIntercom, UpdateSalesforce, UpdateZoom). **Root span** (no parent), parent-child (A→B→C, Fig 5-4). A service can appear multiple times (circular deps, parallel computations).
  - **Five required fields**: trace ID (created by root, propagated), span ID, parent ID (absent at root), timestamp, duration. Useful extras: service name, span name (intense_computation1/2), span attributes (http.response.status_code=200; anything you'd log).
  - Build-a-tracer from scratch in JS: `log(name, attrs)` JSON with timestamp; `logTiming(name, lambda)` adds durationMs; `Span` class with startTime, traceID, parentSpanID, spanID, name, attributes Map, durationMs. Spans = structured logs with fancier fields.
  - **Trace context** = trace ID + span ID + parent span ID (three IDs). Parent IDs let backend build a **DAG**; rendered as tree = waterfall (just one possible visualisation; Fig 5-5: GET /profile/user → get-profile-data, get-profile-photo → get-photo-caption). Context only needs trace ID + current span ID.
  - Passing context: explicit in **OTel Go SDK** (`ctx` passed); implicit via **thread-local** in Ruby/Python; **AsyncLocalStorage** in Node.js. `startSpan(name, lambda)` helper.
- **Deriving views**: shopping-cart span (service, event_name transaction_completed, duration_ms 312.7, status ok, http.method POST, http.route /checkout, status 200, user_id, session_id, order_id, cart...). SQL: `date_trunc('minute')` + `PERCENTILE_DISC(0.99) WITHIN GROUP (ORDER BY duration_ms)` → P99 per minute; add `region` to SELECT/GROUP BY with no schema change. Streaming: quantile sketch per bucket, grace period for late events, **t-digest or HDR histograms**.
  - From one event: recompute P99 with other windows (5m, 1h), filters (device_type='mobile'), conditions (status>=500) without redeploying telemetry config or re-ingestion; derive log narrative or trace by stitching trace.*_id; avoid pre-aggregation pitfalls. "Capture facts, post-decide the shape".
- Conclusion: metrics cheap but lossy and narrow; logs become "congressional library of unindexed prose"; structured logs fragmented per unit of work; traces = interrelated logs with propagated context.
- Interview angles: average-of-averages trap and histogram; counter vs gauge; five fields of a span; how context propagates per language; derive P99 by region from events with SQL; structured log = structured event.

## Ch6 Making Structured Events Arbitrarily Wide (read in full; Jeremy Morrell, Principal Engineer at Cloudflare; figs 6-1, 6-4, 6-6 viewed, others described in text)
**Argument:** A well-instrumented service has hundreds of attributes per event. Catalogue of attribute families with example queries. Put key timings and rollups on the main span instead of only child spans (avoid JOINs). Mark wide events with `main=true`. Domain-specific attributes are the most valuable.

- "Arbitrarily wide" = no practical limit on context per event; high dimensionality + high cardinality; avoid pre-joins.
- **Service metadata** (Table 6-1): service.name, service.environment, service.team, service.slack_channel (link to a service catalog to survive re-orgs). Query: count distinct services per team in prod.
- **Infra** (6-2): instance.id, instance.memory_mb, instance.cpu_count, instance.type (m6i.xlarge). (6-3, OTel k8s semconv): container.id, container.name, k8s.cluster.name, k8s.pod.name, cloud.availability_zone, cloud.region. **PaaS/Heroku** (6-4): heroku.dyno (DYNO env var), dyno_type, dyno_index (split for easy queries), dyno_size, space, region.
- **Build info** (6-5): service.version, service.build.id, git_hash, pull_request_url, diff_url, deployment.at, deployment.user, **deployment.trigger** (merge-to-main / slack-bot / api-request / config-change), **deployment.age_minutes** ("did something just get deployed?"). Threading build data to runtime is glue code but invaluable. Fig 6-1: v1 200s fall as v2 200s rise; brief 500 spike all from v1 → app doesn't shut down cleanly during deploys (group by version disambiguates).
- **Feature flags** (6-6): feature_flag.auth_v2, feature_flag.double_write_to_new_db; compare errors (exception.slug) by flag vs control.
- **Versions** (6-7): go.version, rails.version, postgres.version → Rails CVE: which services on which version; memory heatmap grouped by go.version after upgrade.
- **HTTP** (6-8): server.address, url.path, url.scheme, url.query, http.request.id (x-request-id; x- prefix deprecated but entrenched), method, request.body_size, request.header.content-type, response.status_code, response.body_size, response header. Fig 6-2 heatmap of response body size shows outliers.
  - **User-Agent** parsed at write time (6-9): user_agent.original, device, OS, browser, browser_version. Custom (6-10): user_agent.service, service_version, app (iOS/android), app_version. Don't settle for auto-instrumentation defaults.
- **Route** (6-11): http.route (/team/{team_id}/user/{user_id}), http.route.param.team_id, http.route.query.sort_dir. P99 grouped by route showed only POST /checkout and POST /signup slow (Fig 6-3).
- **Timings on the main span** (6-12): auth.duration_ms, payload_parse.duration_ms. "Wrapping absolutely everything in its own span is the most common failure mode" for new tracing users. Child spans good for one waterfall, hard to query across requests; child-span version needs a self-JOIN on trace_id. Accept slight duplication for fast iterative queries; helps BubbleUp (ch8).
- **Async rollups** (6-13): stats.http_requests_count/duration_ms, stats.postgres_query_count/duration_ms, stats.redis_query_count/duration_ms, stats.twilio_calls_count/duration_ms. Fig 6-4 heatmap: **bimodal** DB query counts (invisible on percentile line charts) + handful of requests making many more queries (N+1 outliers).
- **Errors** (6-14): error, exception.message, exception.type, exception.stacktrace, **exception.expected** (bots hitting missing URLs), **exception.slug** (unique greppable literal string per throw site, e.g. "err-stripe-call-failed-exhausted-retries"; enforce with lint; low-cardinality GROUP BY). Failed request without slug = error handling gap; query `error=true AND exception.slug=NULL`.
- **User/customer** (6-15) "most important metadata": user.id (PII policy if email + vendor), user.type (free/premium/enterprise/vip), user.auth_method, user.team.id, user.org.id, user.creation_timestamp (new vs long-time users), **user.assumed / user.assumed_by** (impersonation; security audit). Single accounts can be **10%+ of revenue** or load; separate their traffic.
- **Rate limits** (6-16): ratelimit.limit (200000), remaining, used, reset_at. Fig 6-5: user suddenly hammered one endpoint until quota exhausted → buggy automation or leaked credentials; check route, UA, source IP.
- **Caching** (6-17): cache.session_info, cache.feature_flags hit booleans.
- **Localization** (6-18): language_dir (rtl/ltr), country (not physical location), currency.
- **Uptime** (6-19): uptime_sec, **uptime_sec_log_10** (sublinear; first minutes visible alongside multi-day instances). Finds reboot issues, memory leaks over time, crash loops. Fig 6-6: linear scale hides crash loop; log scale shows instances run a few seconds then crash → then group by service.version.
- **System metrics on events** (6-20), fetched every ~10s and cached: metrics.memory_mb, cpu_load, gc_count, gc_pause_time_ms, go_routines_count, event_loop_latency_ms (Node.js). Not mathematically sound (only sampled when traffic flows; no rigorous P90 of CPU) but good enough for debugging heatmaps; **don't alert on it**; use real metrics for alerts.
- **`main = true` convention** (6-21): marks the wide event (request/response or background job). `GROUP BY name` on main spans to learn a new system; error rate must filter main=true because http.response.status_code also appears on outgoing child spans.
- **Domain attributes** (6-22): asset_upload.s3_bucket_path, email_vendor.transaction_id, vcs_integration.vendor (2% failing because Bitbucket down), process_submission.queue_length. Most valuable; no framework can do it for you.
- Authors' most-asked question: what custom instrumentation should I add? "It depends."
- Interview angles: what to put on a wide event (by family); why timings on main span vs child spans; exception.slug; main=true; system metrics on spans caveat; log10 uptime; separating enterprise traffic.

## Ch7 Instrumenting Your Code with OpenTelemetry (read in full; Fig 7-1 viewed)
**Argument:** OTel is trace-first: context is the glue. Create spans only for "interesting and aggregable" work, design traces for non-request/response architectures with links and correlation IDs, layer signals deliberately (not duplicate), name consistently, use schemas, and use AI agents for planning + scripted migration.

- Recommends *Learning OpenTelemetry* (Ted Young & Austin Parker, O'Reilly 2024). "Learning cliff".
- Why OTel: open standard for creating/transmitting/interpreting telemetry + **semantic conventions**; less lock-in, fewer migrations, cleaner cost control. Goal: telemetry **native** to libraries, frameworks, runtimes, infra.
- Zero-code instrumentation exists for popular libraries; the hard part is *useful* telemetry. Instrumentation is sculpting (what to keep vs throw away).
- **Trace-first**; "context" overloaded (system state / data structure / values). Two propagation types: **interprocess** (crosses processes, often HTTP headers via **W3C TraceContext**: trace ID, parent span ID, optional **baggage** key-values) and **intraprocess** (methods, threads, coroutines). Example 7-1 Java `W3CTraceContextPropagator.inject(Context.current(), ...)`. Carriers: HTTP, message queue envelopes, env vars, gRPC/RPC headers. In Java, scopes (try blocks); metrics/logs in scope inherit context.
- **Span test**: Is it **interesting** (affects latency/failure)? Is it **aggregable** (group by name/attrs gives useful trends)? Table 7-1: yes for HTTP handler, DB query, external API, cache lookup, queue publish/consume, I/O-bound validation, business transaction/saga; no for private helper, loop iteration (unbounded cardinality), getter/setter, pure-CPU validation, orchestration that just calls instrumented code.
- Too many spans (millions in a trace) vs too few (hours collapsed in one opaque handler). **Conway's law** pull: traces mirror org boundaries; prefer real component/domain boundaries. "Hundred 2ms spans → too many": roll up into one span or attributes; profiling (ch20) for fine-grained.
- Sidebar "perils of auto-instrumentation": errs on too many unactionable spans; you own making defaults sane. Keep traces sampled; emit **histograms for RED** (rate, errors, duration) for HTTP/gRPC alongside traces (cheap, survive head sampling). Drowning? drop/sample instrumentation or summarise into parent span attributes via processors.
- **Streaming** (Kafka etc.): smallest unit isn't most useful; questions are about trace *shape* (stage dwell times, success/fail ratio of stages; step functions/FSMs). Event sourcing: what's the root? Example: orders-api → orders.events topic → payment-svc → inventory-svc → shipping-svc → nightly reconcile-job. Serialize context into message envelope; producer span `messaging.publish` (kind **producer**, not client) with system, destination, message ID, business IDs; consumers create `messaging.process` spans connected by **span links**, not as children. Propagate a hashed unique **transaction/correlation ID** through the pipeline → timeline of traces. Fleet-level: **metric exemplars** (annotate metric point with trace/span). Frontline alerting on metrics: per-stage counters failed_total/processed_total (consumer name as attribute, NOT transaction ID), ratio alerts, histogram of publish→process time with exemplars. Step functions: histogram of stages per transaction; baggage to pass count.
- **Fan-out/fan-in** (POST /render → transcode/thumbnail/caption tasks, join when N succeed or deadline): root = POST; parent-child or producer-consumer; root links children + final summarisation span. Alert on entry point or child tasks per ownership.
- **Long jobs** (nightly ETL, hours/days): avoid "million children trace". Model each stage as own trace linked by links/correlation IDs; or build root span in memory/file with heartbeat/status events and write at end. Don't periodically re-flush root span (most stores don't support span updates → rejected/undefined). Use metrics/logs for intermediate status. If goal is a safety net: one **summary wide event** with hundreds/thousands of attributes at completion.
- **Serverless**: prefer custom instrumentation; one well-designed attribute-rich span per invocation (cold start, memory). AWS Lambda **stateless tracing**: emit lightweight events; stateful **OTel Collector** with custom processors assembles spans (Fig 7-1: serverless runtime with OTel API + stateless SDK → raw events → extension layer with stateful SDK/buffer + Collector → metrics/logs/traces → backend). Platform post-execution hooks often non-OTel → correlate by invocation ID via pipelines, federated queries, or batch/join/normalise.
- **eBPF**: programs in Linux kernel, small, safe (can't corrupt memory/crash), no in-process overhead, enable/disable without restart/recompile. **OTel eBPF Instrumentation (OBI)**: metrics+traces for HTTP/HTTPS and gRPC across languages; propagates context; accelerator/gap filler not replacement; kernel-level network detail; trace through legacy services; populate service maps. Concerns: conflicts with other eBPF programs, elevated permissions (root or specific capabilities). Microsoft eBPF for Windows in progress.
- **Layered telemetry**: right signal at right detail. Benefits: devs layer views regardless of sampling; operators balance accuracy/visibility/cost; consumers drill from symptom to cause. **Three-question test**: needs causality + full request context → **traces**; cheap long-term storage / fast alerting → **metrics**; rare vs common + audit requirements → **logs/events**. Pattern: span + histogram per HTTP request (head-sample traces; histograms for alerting). Billing / SLA conformance data → isolated event-only pipelines. Microscope analogy. Start with traces at service boundaries; layer lower-dimension metrics at same boundary, generated from spans by the Collector.
- Sidebar: accurate metrics from spans hard/impossible under head sampling; OTel probabilistic head sampling support experimental.
- **Naming**: no IDs/variables in names (`GET /users/profile/{user.id}`); dot notation + snake_case; consistent metric names; put units/type in metadata not name (`http.server.request.duration` not `..._ms`).
- **Schema-driven telemetry**: define conventions in schema files; **OpenTelemetry Weaver** validates at compile/runtime and generates code. Brownfield migration: sample existing telemetry, normalise to OTel-flavoured format, create org namespace (service owners, business units, cost centres), check into source control. Conflicting keys for same value wastes incident time and misleads AI. Units as attributes; don't mix units on one key; normalise name/route. **Defence in depth for user data**: hash sensitive values, SDK/Collector allowlists, transform processors for PII; stable reversible hashes via internal scriptable API.
- **Agents** = "models using tools in a loop" (Hannah Moran, Anthropic, 2025). Two modes: **planning** (spec, span boundaries, names, attributes; schema + rules for agent memory) and **execution** (brownfield caution; models imitate most common repo patterns; small reviewable changes). **Automate the automation**: agent writes script to find custom metrics and decide convert-to-attribute/delete/retype. **Telemetry tests** before/after migration; diff proprietary APM agent output vs OTel output. Share rules in VCS; "agent skills". Treat agent rules like software: daily CI job that generates a toy app, instruments, emits to test backend via MCP, evaluates.
- Prompting: clear, concise; no bribes/threats (Padolsey 2024). Patterns: manage context (subagents, external markdown task file; recency bias), small chunks + commit often, disposable tools (even build your own agent), AI writes docs/schema of current state, bring observability into the dev loop (agent queried P50/P99/P9999 result-set sizes to pick page size).
- Interview angles: inter vs intraprocess propagation; W3C traceparent; when to create a span; span links vs parent-child for Kafka; exemplars; long-running job tracing; serverless; eBPF/OBI; layered signals 3-question test; naming rules; Weaver; PII defence in depth; AI-assisted migration.

## Ch8 Getting Started with Observability Analysis (read in full; figs 8-1, 8-2 viewed; 8-3 described)
**Argument:** Traditional debugging works from known conditions (intuition, runbooks, dashboard pattern-matching). High-observability debugging works from first principles via the **core analysis loop** (hypothesis-driven: propose, test, refine), which is teachable and democratic, and which can be automated (BubbleUp-style baseline vs anomaly diff). Gen-AI agents come as copilot/commander/caretaker; their quality depends on telemetry quality and context.

- Senior engineers' "magic" = accumulated scar tissue (memorised failure modes, which dashboards to check). Managers push runbooks; mostly wasted because modern systems rarely fail the same way twice (and recurring failures get automated remediation). Long thin tail of rare problems; "five impossible conditions align" once every few years.
- Runbook sidebar: keep essentials: owning team, how to reach on-call, escalation, dependencies both ways, links to good entry-point queries/dashboards. Comprehensive failure/resolution docs go stale; **wrong docs are more dangerous than none**; **instrumentation is the best documentation** (intent + live state).
- Even with wide events you can still debug from known conditions (tail -f | grep; infinite dashboards; flipping dashboards pattern-matching shapes). "Collecting better data isn't what lets you debug unknowns; how you analyse it is."
- Honeycomb early days examples: frontend feature → max css_asset_size / js_asset_size by build_id; new customer → filter team_id, P95. Still known conditions.
- **First principles**: treat understanding as provisional until verified by evidence; scientific method; multicausal issues ("13 different things").
- **Core analysis loop** (Fig 8-1, four steps in a cycle): (1) What are you trying to understand? (what did the customer/anomaly/alert say) (2) Visualise telemetry to verify/find the performance anomaly (change in a curve) (3) Search for dimensions common within the anomalous area but not the baseline: look at sample rows for outliers; slice by dimensions (experimental GROUP BY status_code); filter (4) Has this isolated likely dimensions? If not, filter to isolate and return to step 3. Brute-force over all dimensions; correlation ≠ causation. Works regardless of system familiarity.
- **Automating the brute force**: compute all dimension values inside the selected area vs outside (baseline), diff, rank. Example output: request.endpoint=batch in 100% of anomaly vs 20% of baseline; handler_route=/1/markers/ 100% vs 10%; user_agent populated 97% vs 100%.
- **Honeycomb BubbleUp**: draw box on heatmap; histograms blue=baseline, orange=selection; sorted by difference. Fig 8-2 "63 interesting dimensions found". Real incident: **global.availability_zone=us-east-1a in 17% baseline vs 98% anomaly** → a particular instance type in one AZ slow → unreported cloud-provider network issue for the whole AZ, verified with provider and customers.
- Metrics lack dimensionality; logs need IDs + heavy postprocessing to become events. "If it can't be done manually in your tool, it can't be automated." Automation removes repetitive comparison; humans interpret/decide. No need to seed app-specific intelligence.
- **AIOps** term coined by **Gartner in 2017** (ML for alert noise/anomaly detection). 1st edition: let computers crunch, humans add context. Gen AI may do both.
- "Telos of observability is understanding, and through it improvement."
- **Agent personas**: **copilot** (beside human; human steers and evaluates; e.g. ChatGPT/Claude Desktop analysing stack traces, trace screenshots), **commander** (human sets goals like "why is my service slow?"; agent uses tools to write/run code, query data; e.g. Cursor, Claude Code; weaker transfer of understanding to operator), **caretaker** (autonomous, passive observer with strict goals; e.g. after deploy check endpoints with new flags vs ticket goals; on alert gather info and post 3 hypotheses in incident channel; needs heavy knowledge transfer). Papers cited on LLM root-cause/mitigation for cloud incidents.
- Where does context live (human or agent)? Telemetry quality paramount; small naming inconsistencies hurt AI more than humans. Error compounds with autonomy (copilot: restart session; caretaker: errors cascade, data loss). **Humans own outcomes.**
- Agents are "optimized for confidence"; "hallucinations" often rational inferences from missing implicit knowledge; agents reconstruct state each time, run several wrong queries.
- **slow_request example**: field true when >300ms; agent concluded requests slow *because of* slow_request (maybe load test or flag). Adding a field description made it ignore the field. → AI needs accurate succinct docs, semantic consistency, human-readable descriptions, ability to search/enumerate telemetry, freedom to iterate + guardrails against destructive actions. What helps agents helps humans.
- Interview angles: walk through core analysis loop on a latency spike; why runbooks fail; BubbleUp mechanics (implement it!); copilot/commander/caretaker; field descriptions for AI.

## Ch9 Observability-Driven Development (read in full; no figures)
**Argument:** ODD bundles instrumentation with features so it's in production while intent is fresh. TDD verifies against a spec in a controlled environment; ODD verifies against reality. Observability is the telescope that aims the debugger/profiler microscope. Put engineers on call for their own code; reduce batching; use AI with explicit instrumentation standards and schemas.

- TDD: gold standard for ~20 years; controlled environment (data reset, mocks, no variability); deterministic; but passing tests ≠ good user experience in prod, ≠ easy localisation. "TDD ensures correctness against a specification; ODD verifies behaviour against reality."
- Debugging is easiest right after shipping; cost grows (orders of magnitude) the longer detection is delayed; intent fades.
- Observability operates at the order of **systems, not functions**; line-level verbose logging swamps storage. Observability narrows search space (which component, which hop, which users, build ID, infra slice, request path). Then use debugger (**GDB**) or profiler (ch20); copy full context from the trace to reproduce locally.
  - Path 1: latency spike → group by endpoint at edge → avg/P90/P99 → trace slow request → timeouts start at service3 → reproduce locally in debugger.
  - Path 2: only write endpoints slow → group by DB destination host → some primaries → particular instance type/AZ → infra problem, not code.
  - **"Observability is the telescope that helps you aim the microscope."**
- Microservices: debugger can't hop the network. Early phrase "**strace for microservices**". Slowness could be: code bug, user usage pattern change, DB over capacity, network connection limits, misconfigured LB, service registration/discovery, or a combination; low-observability = all graphs spike together.
- Instrumentation drives observability: context like build IDs, host groups, instance types, kernel versions, dependency targets, container versions. PR question: **"How will I know if this change is working as intended?"** Cache example: attributes cache.put, cache.get, cache.key, cache.hit.
- **Put engineers on call**: auto-page the person who just merged for **30–60 minutes** after deploy. Not punishment; ownership. Four post-deploy questions: Is code doing what you expected? How does it compare to the previous version? Are users using it? Any abnormal conditions?
- Advanced: test against subset of prod via flags or routing select requests; feedback in seconds/minutes. Start at the edge and work to the answer every time "no guessing, intuition, or prior knowledge" → operations as science.
- **Shift observability left**: teams that can't reason about prod treat it as fragile: **"glass castle"** → reflexive rollbacks. ODD turns it into an "interactive playground". Must be shared engineering practice, not just SRE/ops.
- **Accelerate** (Forsgren, Humble, Kim 2018): speed vs quality trade-off is a myth; elite performers improve both. **North Star metric: lead time to production** (code written → running in prod). Ways to speed delivery: **reduce batching** (one coherent change, one merge by one engineer; batching is the greatest cause of deploys that break and take hours/days to untangle); **invest in the deployment pipeline** (experienced owners, not the intern; everyone understands and improves it; ch18).
- **ODD with AI**: copilot model. "Add OpenTelemetry support" usually works, but working ≠ useful: agents invent attributes, duplicate signals, over-detailed traces. Put instructions in agent config under one header, direct. Examples: spans are primary signal, preserve context; put HTTP handler attributes on root span; don't duplicate, layer; every route handler must have app.customer.id and app.customer.plan_type from request context 'customerId'/'plan'. Give source mappings, docs, OTel standards.
  - Footnote: AI tools to $100M ARR: GitHub Copilot (Jun 2022, ~12 months), ChatGPT (Nov 2022, 6–9 months; $1.3B ARR by Oct 2023), Cursor (Apr 2023, ~12 months), Replit Agent (Sep 2024, ~8 months), Lovable (Nov 2024, ~8 months).
  - "All code is technical debt" / carrying cost. Honeycomb internal: **AI-coauthored commits 3.4x longer and 5.5x net impact** (607.4 vs 177.8 lines; net 444.1 vs 81, over one quarter). Reduce carrying cost: centralised helper libraries of attribute constants/methods; reusable migration prompts mapping variables→attributes.
  - Blend TDD+ODD: **OTel Weaver** schemas as static CI checks; give agents schemas + local validation of emitted telemetry; tight automated verification loops.
- Interview angles: TDD vs ODD; telescope/microscope; "how will I know it works?" in PRs; on-call for the merger; glass castle; lead time; batching; AI instrumentation guidance.

## Ch10 The Role of AI Agents for Observability (read in full; Boris Tane, Founder/CEO Coreplane Labs; figs 10-1, 10-2 viewed)
**Argument:** Agents add value doing multistep investigations, translation of telemetry, and instrumentation quality, but success or failure comes down to **context**. Naive natural-language querying fails in large messy systems. The senior engineer's mental model is eroding as coding agents ship code, so teams must build and maintain an explicit, machine-readable context layer.

- Authors' note: this chapter will "age in dog years"; durable principles: instrument richly, preserve context, design strong feedback loops, know where automation helps vs where judgment is needed. "Observability has always been about the tension between context and precision."
- Agent for observability: LLM reasoning engine + tools (query DBs, call APIs, write/run code, trigger workflows); pursues goals across steps, adjusts.
- **Fig 10-1 sequence**: P1 alert high error rate on checkout → agent queries telemetry store for error-rate/latency → "error rate spike at 14:32, p99 +340ms" → fetch slow/failing traces → 3 trace patterns → query correlated logs → timeout errors payment-service → stripe-client → look up stripe-client retry config in codebase → **retry timeout set to 2s, upstream SLA is 5s** → root-cause summary + suggested fix. Parts already work today; agents go round in circles with disparate, poorly labelled data.
- **Pitfalls of querying without context**: (1) agent doesn't know what it doesn't know (no hypotheses from history: flaky upstream since migration, normal Tuesday vs post-long-weekend Tuesday); (2) **naming chaos** (user-service, users-svc, svc-user, legacy-user-api) → confident wrong conclusions; (3) enormous data surface (millions of spans/min); (4) correlation vs causation (need topology/causal model). Works in small well-named systems; breaks in large messy ones that matter.
- **Proven use cases**: (1) **incident response**: first ~15 minutes of mechanical steps (dashboards, recent logs, recent deploys, blast radius); parallel queries; structured summary; augment on-call, don't automate end-to-end. (2) **explaining errors/patterns**: translation, e.g. trace shows sequential DB calls = classic **N+1 from ORM misconfiguration**; helps juniors. (3) **improving instrumentation quality** at authorship time (encode wide events, naming, log levels). Generic "add observability" without conventions → compiles but useless.
- **Adjacent**: **alert quality audits** (hundreds of alerts, silently acked; correlate with incident history; flag always-firing never-actioned; propose thresholds; continuously); **SLO proposals** grounded in observed data, trend detection before breach (ch11). Work everyone agrees matters but deprioritises because cost is "diffuse and deferred"; agents remove activation energy.
- **Disappearing mental model**: services accrete; names drift; docs 18 months stale; critical path across 4 languages, 3 clouds, one untouchable legacy service; quirks known to two people (one left). Examples: auth-proxy and api-gateway are the same service; orders-v2 actually processes checkouts; inventory telemetry partially broken since Q3 migration.
- **Six context layers** (Fig 10-2): **service topology**, **naming conventions** (canonical names, aliases, owners), **deployment context**, **known issues**, **recent incidents** (last 30 days; blast radius; was root cause confirmed?), **business context** (revenue-critical endpoints, acceptable thresholds). Poor context → generic queries → incomplete picture → wrong/shallow conclusions; rich context → targeted queries → relevant signals → accurate diagnosis. Model alone isn't the differentiator.
- Coding agents remove engineers from details → institutional knowledge forms more slowly → must be maintained explicitly. Engineer role shifts from execution to direction (set context, review, judge at boundaries). "The context problem is yours to solve."
- Next: SLOs focus on "who and what"; observability explains "how and why".
- Interview angles: how you'd build an incident-triage agent safely; why NL querying fails; context layer design; agent for alert hygiene.

## Ch11 Using Service Level Objectives for Reliability (read in full incl. full LLM prompt examples; no figures)
**Argument:** Threshold (potential-cause) alerts cause alert fatigue and only cover known-unknowns. Helpful alerts = reliable indicator of degraded UX + actionable. SLOs with event-based SLIs alert on symptoms ("what"), observability explains "why". ANZ Bank case study: standardised OTel telemetry let them launch with SLOs in 12 weeks. LLMs solve the blank-page problem for SLO targets and SLI expressions; encode standards in versioned prompts.

- Threshold examples: CPU >80% for 5 min, memory <10%, disk nearly full, thread count. CPU spike could be backup job, GC, real outage, or circuit breaker. "Don't worry, the process runs out of memory sometimes..."
- **Normalization of deviance**: term from the **Challenger** disaster investigation. Ignoring alerts → the real alert fights "learned distrust". Post-incident reviews add alerts → alert escalation. Vendors "productized deviance" with AIOps grouping/suppression.
- **Known-unknowns**: aware they exist, not whether/when: disk 95% full, queue depth >70%, TLS cert expiring in 10 days, error rate >10% for 5 min. Distributed systems: failure modes become **combinatorial**; codifying every remembered outage = unwinnable arms race. **Unknown-unknowns**: emergent behaviours, cascading retries, partial brownouts, dependency timeouts under specific traffic mixes, harmless deploy tipping downstream cache into eviction churn → "default tax for scale and complexity".
- Thresholds fuse symptom with cause; at 2 a.m. move uncertainty into the incident channel. Self-healing (autoscaling, failover, circuit breakers, LB) shouldn't page; investigate in business hours. "Manufacturing burnout."
- Google SRE book (Murphy, Beyer, Jones, Petoff 2016; Ewaschuk & Beyer "Monitoring Distributed Systems" pp63–64): good alert = urgent user impact, actionable, novel, requires investigation not rote action. Book's two criteria: (1) **reliable indicator UX is degraded**; (2) **solvable/actionable** via systematic debugging without divination.
- UX is the North Star; symptom-of-user-pain alerts > potential-cause. Static thresholds fail with varying traffic (10 slow users significant at hundreds of sessions, not at tens of thousands); transient failures (retry success, reroute) more visible in P95 at low traffic. Time-bucketed metrics (P95 per 5-min interval → whole interval good/bad) → false positives AND negatives, coarse diagnosis.
- **SLOs**: internal goals, stricter than external **SLAs**; popularised by Google SRE book. Recommend **Alex Hidalgo, *Implementing Service Level Objectives* (O'Reilly 2020)**. SLOs without observability can have severe unintended consequences. Based on critical user journeys. **SLIs** classify good/bad: **time-based** ("P99 < 300ms over each 5-min window") vs **event-based** ("proportion of events < 300ms over rolling window"). Recommend event-based (more reliable, granular; ch12 explains).
- SLI example: events with path /home; OK if duration <100ms and successful; ≥100ms = error even with success code → spends error budget.
- SLOs decouple **what** (users hurting) from **why**; actionable because responder debugs with observability (start wide, filter). "Delete all of your unactionable alerts"; may need cultural shift.
- **Case study (Mat Vine, Cloud, Quality & Reliability Lead, ANZ Bank)**: build SRE practice in transformation arm; boss wanted pilot launch readiness in **12 weeks** vs his estimate **12–18 months**. Google Cloud partner; leadership educated via Google's Customer Reliability Engineering (CRE) program and SRE book; cloud-native, mostly in-house; early OTel bet. Rapid development = poor conditions. Rejected threshold alerting as a "one-way trap" (thresholds calcify; "whatever performance we have today" = alert on statistical deviation not customer impact). ## Ch12 Acting On and Debugging SLO-Based Alerts (read in full; figs 12-4,12-5,12-7,12-9,12-11 viewed; Go code read in full)
**Argument:** Error budgets + burn alerts give early warning. Use a 30-day sliding window, forecast with relative or predictive (short-term or context-aware) burn alerts, baseline ≈ lookahead/4, run multiple lookaheads. Event-based SLIs beat time-series good/bad minutes, especially for stringent SLOs and brownouts, and let you backfill SLI changes.

- Error budget = max unavailability tolerated. 99.9% time-based: **8h 45m 57s/year, 43m 50s/month**. Event-based: running tally of good vs bad events; budget scales with request count. Out of compliance when whole budget spent. Higher target → less reaction time. Preemptive burn alerts work best for SLOs up to **99.95%** (≈**21m 54s/month** full downtime); above that mainly reporting/warning. See *The Site Reliability Workbook* ch5 (Beyer et al., O'Reilly 2018).
- **Window**: fixed (calendar) vs **sliding (trailing 30 days)**. 30 days most pragmatic; 7/14 don't match customer memory or planning; 90 too long (burn 90% in a day and still "pass"; incidents don't roll off). Fixed windows reset abruptly ("refund on the 31st doesn't make them tolerant on the 2nd"); human emotions/recency bias don't reset monthly. Sliding window burns/restores smoothly.
- **Zero-level alert** = budget exhausted. Sidebar: when negative, shift from features to stability; feature freezes; see Hidalgo for policies. Forecasting beats heroism for morale.
- **Three burn-alert models**: (1) **threshold-crossing** (e.g., <30% remaining): just moves the goalpost; teams then act as if empty → needless feature freeze. (2) **Relative burn** (SRE Workbook): compare observed failures in lookback window (e.g. 15 min) with allowed proportion. Worked: 10M req/month, 99.9% → 10,000 failures allowed; **2,880** 15-min windows/month → ~3.4 failures per window; **4x alert >13 failures**; **20x alert >68 failures** in trailing 15 min, regardless of successes. Aware of total expected request rate, so 1 of 20 failing at low traffic doesn't fire (vs naive 0.1/0.3/2% error-rate thresholds). (3) **Predictive burn**: lookahead + baseline (lookback).
- **Lookahead**: 99.9% target trending to 99.88% in a month → next business day ticket; trending to 98% within an hour → page. Traffic is cyclical (cron every few minutes; daily/weekly/yearly seasonality, retail holidays). Baseline should be same order of magnitude as lookahead. **Rule: linear extrapolation up to 4x without seasonality compensation** (4h alarm from last 1h; 24h alarm from last 6h). Same maths as sprint burndowns/capacity planning.
- **Short-term (ahistorical)** vs **context-aware (historical)** burn alerts. Trade-offs: compute cost vs sensitivity/specificity; philosophy: should remaining budget affect urgency (10% left vs 90% left)? Units: time-series units (minute good/bad) or events.
- Short-term worked example: 99% over 30 days, 43,800 units/month → budget **438**. Last 24h 1,440 units/50 failed; last 6h 360/5. Linear: 5 in 6h → 20 more in 24h → 25 total < 438, fine. Using 1 day: 50/day → 400 more in 8 days → 450 > 438 → exhaust in ~8 days. Traffic varies (one error overnight at 1/10 traffic ≈ 30 errors next day). **Proportional extrapolation** example: last 6h 50 units, 25 failed (50%) → linear says 100 more (105 total, fine) but proportional says 50% × 1,440 = **720** > 438 → exhausted in ~half a day → page.
- **Context-aware**: rolling totals over entire SLO window; expensive. Honeycomb: small SLO datasets suddenly cost **>$5,000/day in AWS Lambda** vs tens of dollars/day for user queries → **caching** required. Example: 26 days 37,960 units/285 failed; last 24h 1,460/130; project 4 days using 1-day baseline; **26 lookback + 4 projected = 30-day window** (Fig 12-7). Steps: sum past 26 days; baseline last day rate; extrapolate 4 days; compute window as it'll look in 4 days; alert if exhausted. Fig 12-8: 65% remaining at start of baseline day → 35% now (30% burned in a day) → alert.
- **Go `isBurnViolation`**: pOffset = ExhaustionMinutes/lookbackRatio; pWindow = now − pOffset; tWindow = now − TimePeriodDays + ExhaustionMinutes; scan timestamps backward until before tWindow, accumulate running totals/fails; if within pWindow add lookbackRatio × values to projected; projected += running; allowedFails = projectedTotal × BudgetPPM / 1e6; violation if projectedFails != 0 && projectedFails >= allowedFails. (POC candidate.)
- **Baseline window**: 15 min to project 3 days → false alarms; 3 days to project 1 hour → too late. Multiple burn alerts with different lookaheads can fire in "illogical" order (2h alert fires, 1-day doesn't) because baselines differ; **act on either**. Hourly windows for sudden changes; daily for sprint prioritisation.
- **Acting**: diagnose burn type: gradual steady (Fig 12-9: 51.4% remaining), bursts (Fig 12-10: 31.4%), big one-off drop (Fig 12-11: down to 1.3%). Fig 12-12: 30-day cumulative state over 90 days; recovery when a dip ages out. Burn-all-at-once vs slow burn suggest different failure types.
- **Events vs time series for SLOs**: time-series unit = slice of time (did the whole system succeed?). For **99.99%+**, budgets exhaust in minutes/seconds; human acknowledge+login+remediate ≈ 3+ min → need automated remediation. P95<300ms per-minute SLI: must wait for minute end; if only 94% <300ms the whole minute is bad → burns **25% of the 4.38-minute monthly budget** in one shot. **Amazon CloudWatch fee-free default is 5-minute windows** → one bad window breaches. Mitigations: auto-remediate after 3 synthetic probe failures; instantaneous failing % at high volume. Events: 94% good → only 6% counts against budget.
- Brownouts > blackouts. **1% brownout of a 99.99% system ≈ 100% outage of a 99% system**; either way >7 hours before monthly budget exhausted (99% of 30 days = 7.2h).
- Events can be precomputed into SLO data but not vice versa → **backfill SLI/SLO changes** from raw data instead of waiting months. Five nines needs every mitigation (auto-remediation on granular accurate data).
- Event data also tells you which users, dependencies, behaviour combos are failing after a burn alert.
- Interview angles: compute error budget minutes for N nines; sliding vs fixed; relative burn maths (10M/99.9/15min); proportional vs linear extrapolation; 4x rule; multiwindow; why event-based SLIs; brownout equivalence; cost of context-aware computation.

## Ch13 Efficient Data Storage with Retriever (read in full, 54k chars in two passes; figs 13-2, 13-5, 13-6 viewed)
**Argument:** Observability storage must: return queries in seconds; query any field at full resolution with no privileged dimension except time (and service/tenant partition); expose fresh data within seconds; be durable and fault-tolerant. TSDBs (cardinality explosion), NoSQL (indexes), RAM-based Scuba (cost), row stores like Bigtable (compaction, locality groups) all fall short. Honeycomb's Retriever: time-partitioned segments, column-per-file within segment, read-time aggregation, tiering to S3, serverless MapReduce with "RPC impatience", Kafka for durability.

- **Functional requirements**: (1) fast (coffee test); (2) any field queryable, unaggregated; all dimensions equally fast → index everything (prohibitive) or be fast without indexes; (3) only time + service partition privileged; (4) fresh data within seconds (stale data → red herrings); (5) durable, fault tolerant, survive your own infra failures (else observability down while debugging outage).
- **TSDB**: histograms bucket values (Fig 13-1). High overhead creating a new series; cheap appends. Query cost = finding matching series. Converting each dimension to a tag → a new series per unique combination (Fig 13-2: 5 series → 20 when user ID added) → **cardinality explosion**; row-creation overhead linear with events.
- **NoSQL** (MongoDB, CockroachDB): ingest fine; arbitrary multi-dimension queries slow without indexes; unique values make index as big as table; indexes on all columns > data.
- **Scuba**: huge RAM for full scans (Abraham et al., VLDB 2013); infeasible outside Facebook. **1 TB RAM ≈ $5,000 vs 1 TB SSD < $50**; limits query window to minutes.
- Tracing backends (1st ed era, Jaeger): Cassandra, Elasticsearch, OpenSearch, ScyllaDB, InfluxDB. **Grafana Tempo** (v2) purpose-built for tracing but not unified-observability querying. **Observe Inc.** on **Snowflake** (warehouse, less interactive). None manage multiple signal types. **ClickHouse** now de facto OSS component.
- **Row vs column**: Bigtable row-based (Dapper originally on Bigtable): fast single-trace retrieval with sorted primary key; out-of-order inserts cost; mutable (in-memory mutation log + overlay files) → **compaction** expensive I/O; write-once-read-many observability conflicts (compact constantly or read stacked overlays). **Locality groups** read entire group. **Dapper paper: indexes on 3 fields (service, host, timestamp) = 76% the size of trace data.** Pure column stores (Dremel, ColumnIO) need manual coarse sharding (tablename.20250820...) → painful. → **Hybrid**: partition by time + columns. "Fast results matter more than exhaustively complete."
- **Retriever segments**: append to tenant's active **segment**; track oldest/newest timestamp; finalise at **1 hour, >250,000 records, or >1 GB**; metadata windows may overlap. Query reads only overlapping segments (Fig 13-5). Benefits: no strict sort needed if consistent lag; segments append-only and frozen (no overlays/compaction). Weakness: backfilled data mixed with current widens segment windows (batch job reporting old timestamps); could add smarter partitioning/rewrite.
- **Column files**: one append-only file per field per segment + timestamp index; each column file = array of (sequence number, value). Encodings: **dictionary**, **sparse/presence bitmask**, **run-length**; numeric: **delta encoding**, strip trailing zeros, split float exponent/mantissa; hex trace/span IDs → integers; booleans → **roaring bitmaps**; then **LZ4** (decompression speed > ratio). Column creation cost amortised over values → don't create one-use columns like `timestamp_2025061712345`; use key/value. Ad hoc aggregations / virtual columns instead of duplicating data.
- **Six-step query**: (1) find segments overlapping time range; (2) per segment, open only referenced columns; check row timestamp first; (3) emit values for matching rows, advance all offsets; row-at-a-time (low RAM); implicit GROUP on time buckets (e.g. 24 five-minute windows over 2h); (4) aggregate within segment per GROUP (COUNT, SUM...); unload files; (5) merge across segments per GROUP on one worker; (6) sort, **top K** groups (default K). Pseudocode with map[Key]Aggregation (Count, Sum, Max). **t-digest** for P99; **HyperLogLog** for COUNT DISTINCT.
- **Calculated fields at read time**: `COALESCE($session.id, $session_id)` for a rename migration; regex extraction `INT(REG_VALUE($message, "status_code=([0-9]+)"))` ad hoc or as synthetic column. Lightweight **per-segment full-text search corpuses** for n-grams/keywords.
- **Traces as queries**: root spans = `trace.parent_id is null`; waterfall = SELECT timestamp, duration, name, parent_id, span_id WHERE trace_id = X. Enables comparing a span's duration to similar spans across traces. Special-casing trace_id as an index helps single-trace view but loses span decomposition.
- **Joins**: route all spans of a trace to same partition by trace ID; single pass building in-memory maps for left/right; emit "virtual row" on match (left.span_id = right.parent_id) for "parent has X", "root lacks Y", "any child has error". Sliding time window of viable joins sized by available memory. No arbitrary multi-pass joins (would need shuffle); unlike ClickHouse.
- **Real-time**: open column files always queryable; query process forces flush of partial files (separation of ingest and query via filesystem). Alternatives: query RAM structures; force flush every few seconds (costly at scale).
- **Tiering**: recent minutes on local SSD; closed segments older than X compacted and uploaded to **Amazon S3** (or GCS); fetched into memory and unpacked for queries.
- **Parallelism**: MapReduce-style on serverless (AWS **Lambda**) over S3 can beat local SSD single worker; each Lambda maps one+ segments; intermediate merges; central reducer. Tail latency: last 5–10% can take tens of seconds or never finish → **"RPC impatience"**: when 90% done, re-request remaining 10% in parallel without cancelling; first response wins (~10% extra cost).
- **High-cardinality GROUP BY**: fan out reducers by hashing groups onto a ring (**Chord**-style); worst case limit groups by memory, estimate top survivors for ORDER BY/LIMIT, or abort ("2,000-pixel graph can't show 100k lines").
- **Scaling/durability with Kafka** (*Kafka: The Definitive Guide*, Shapira et al. 2021): ordered durable buffer; offset 1234567 always precedes 1234568; stateless **receivers** validate and produce to topic/partition; stateful **indexing workers** consume in order; Kafka retention hours–days (DR replay). Partitions per write workload; query all matching segments across partitions; spans of a trace routed to same partition by trace ID; leader merges; **automatic rebalancer** moves clients/partitions. Redundancy: multiple deterministic ingesters per partition produce identical segments; one uploads to S3, peer spot-checks. Restart from checkpointed offset; replace node from snapshot + offset. Ingest and query separate processes sharing only filesystem → query spikes don't stall ingest; serialization issues only delay ingest.
- **Scale (Nov 2025, US prod)**: ~**1,500 Graviton4 vCPU** receivers, **240 Graviton2 vCPU** Kafka brokers, **2,000 Graviton3 vCPU** ingest+query, bursts to **200,000 Graviton2 vCPU** Lambda; ~**1.5 PB** columnar data in **>1 billion** segment archives (two months retention); ingests **3–5 million spans/s** (up to 20x before client sampling); ms lag; dozens of queries/s; **median 50 ms, P99 5 s**; routine queries scan hundreds of millions of records.
- Build-your-own: Honeycomb's half-dozen "macroservices" don't scale down; single-binary **ClickHouse** better for small. "If your problems are too hard to solve, you probably have the wrong data abstraction." Avoid Elasticsearch/Cassandra for this. Other columnar options: ClickHouse, **BigQuery**, **Apache Druid**. "Enabling high-cardinality exploratory observability is a solved problem."
- Refs: Sigelman et al. Dapper (2010); Welch LZW (1984).
- Interview angles: design an observability datastore (requirements → segments → columns → query → tiering → parallelism → Kafka); why not a TSDB/Elasticsearch; hedged requests; cardinality explosion; how traces are queried in column store; real-time freshness.

## Ch14 Efficient Data Storage with ClickHouse (read in full in two passes; ClickHouse team: Rory Crispin, Vlad Seliverstov, Xander Garbett, Dale McDiarmid; figs 14-1, 14-3, 14-16 viewed; replication sequence 14-6..14-12 described in text)
**Argument:** ClickHouse (open source columnar DBMS, single binary, homogeneous nodes) meets observability needs via MergeTree (immutable sorted parts, sparse primary index, granules), lazy materialisation, SQL, OTel Collector exporter, query-time ASOF joins, skip indexes/projections/materialized views/Merge tables, TTL tiering, replication via Keeper, sharding via Distributed tables, and SharedMergeTree in ClickHouse Cloud.

- Requirements restated: flexible schemas, several million rows/s ingest, interactive over trillions of rows. ANSI SQL → no query lock-in. Vendors on ClickHouse: **Dash0, SigNoz, SolarWinds**; **HyperDX** (MIT-licensed UI built by ClickHouse, Lucene-style syntax). Correlate with non-observability/business data at query time.
- **MergeTree**: table = many **parts**, columnar, sorted by ordering key; **one part per insert** (thousands of rows) → no coordination overhead; parts immutable; background merges up to **150 GB** default max. Like an **LSM tree** but columnar and explicitly ordered by user key. Lightweight updates/deletes exist but keep off hot path.
- Insert steps (Example 14-1 `events` table, PRIMARY KEY (ServiceName, Timestamp)): **sorting** by primary key; **sparse primary index** = first key of each **granule** (~8,000 rows; default **8,192**) (Fig 14-1); columnar write + compression (**20:1 or more** typical for observability); part finalisation (immediately queryable, late data fine); **partitions** = coarse, low-cardinality groups of parts (never merged across); fine-grained partitions hurt.
- **Query execution** (Example 14-2: Message for kube-system between two times, ORDER BY Timestamp LIMIT 1000): (1) partition pruning (e.g. toStartOfDay); (2) part pruning by min/max key metadata; (3) binary search sparse index → candidate granules; (4) read ServiceName/Timestamp columns of granules, filter rows, then fetch Message only for matching rows = **lazy materialization** (like Retriever: unreferenced columns never read).
- Structured columns (HttpMethod, HttpStatusCode UInt16, HttpPath) beat LIKE on strings, but column-per-attribute doesn't scale with fast-changing attributes. **Map(String,String) CODEC(ZSTD(1))** LogAttributes: flexible, but reading a key reads all keys/values; map keys can't be in primary key → use sparingly. **JSON type (2025)**: auto-creates concrete columns for frequent fields, rare data in blob with type hints; nested JSON; overcomes Map performance.
- **Primary key design** follows query patterns: (ServiceName, Timestamp) if service first; (Timestamp, ServiceName) if all services in a time window. No single key fits all → projections/materialized views.
- **Caches**: **query cache** (whole results keyed by AST; enable per frequent query to avoid thrash); **query condition / predicate cache** (1 bit per granule per condition, e.g. threshold > 10 → skip granules next time); **filesystem cache** (fast local disk in front of slow object store; data, metadata, Parquet files); **userspace page cache** (in memory, managed by ClickHouse rather than kernel/tmpfs).
- **Ingest via OTel Collector + ClickHouse exporter** (defaults follow OTel Logs model for small/mid workloads). Fewer, larger inserts → **batch processor** at a central gateway. No gateway (DaemonSet/sidecar) → **async_insert=1** (server-side batching); **wait_for_async_insert=1** (confirmed, retries, backpressure) vs 0 (fire-and-forget). **Idempotent inserts**: block hash retained; exact duplicate inserts deduplicated → safe retries.
- Alternatives: durable buffer in **Kafka or S3** then **Kafka table engine / S3Queue**; their cluster handles **tens of millions of inserts/s** without needing it for performance. Many formats/clients; PostgreSQL table engine; HTTP interface for webhooks (e.g. **PagerDuty**). "Treat observability data as just another data problem."
- Queries: Example 14-3 nginx last hour Message LIKE 'exited%' (HyperDX: `ServiceName:nginx and Message:exited*`). Example 14-4: per Path count, `quantile(0.95)`, `quantile(0.99)` of RequestTime, HAVING Requests >= 100, ORDER BY P95 → Table 14-1: /api/v1/orders 40,723 req P95 1.034s P99 1.78s; /api/v1/users 23,161 0.699/1.08; / 56,093 0.555/0.895; /static/img 20,088 0.491/0.82. Volume + tail latency + prioritisation; group by path+version+remote IP impossible in metrics.
- **ASOF JOIN** (connect ordered events at query time without trace IDs): failures (events: container exited abnormally with signal 9) ASOF LEFT JOIN kube_events (ContainerReady) on ContainerId and recovery.Timestamp >= failure.Timestamp; `dateDiff(second, ...)` → nginx 961s (~16 min), apiserver 63s. Add image_tag → MTTR per image version. Metrics on demand from raw events.
- **Scaling vertically**: profile with **system tables**; hypothesis-driven tuning.
- **Within a table**: **skip indexes** (granule-level metadata; effective when values cluster with primary key order and few granules match; else bloat/slower). Example 14-6 (from default OTel logs schema): `bloom_filter(0.001)` on RequestId (0.1% false positive; GRANULARITY 1 = one granule of 8,192 rows); bloom filters on `mapKeys(LogAttributes)` and `mapValues(LogAttributes)` (0.01); **tokenbf_v1(32768, 3, ...)** on Message (32 KB filter, 3 hash functions; tokens of "The quick brown Jabberwocky"). **MinMax** index for outliers (Duration > threshold; Fig 14-2). **Inverted indexes** for full-text (like Retriever's **Bleve**-based FTS). **Column materialization** (pull hot map keys like pod_name, region, query_id to columns; JSON type does it automatically; convergent with Retriever calculated fields). **Projections** (hidden, auto-maintained reordered/pre-aggregated copy with different primary key; optimizer picks automatically; storage+ingest overhead).
- **Across tables**: **incremental materialized views** = AFTER INSERT trigger writing transformed/aggregated rows to target table; atomic with dedupe; chainable (Fig 14-3: logs_null → all_logs; error_logs_mv WHERE SeverityText='error' → error_logs → error_logs_agg_mv → error_aggregates for alerting); different retention per table. **Merge table** (`merge('system','^query_log.*')`) = unified view over tables with different schemas/partitioning/sort; evolve schema (int→enum status codes; promote user_id from map) without rewriting history; ≈ Retriever COALESCE. Fig 14-4 logs_null split into error/non-error tables, queried via Merge.
- **Lifecycle/TTL**: hot SSD/NVMe → object storage (S3, GCS, MinIO, Azure Blob) by age or disk fill. Unlike Retriever (eager S3 offload for parallel readers), ClickHouse keeps data local while likely queried. `ALTER TABLE events MODIFY TTL Timestamp + INTERVAL 90 DAY TO DISK 's3_ia_disk', Timestamp + INTERVAL 365 DAY DELETE`. TTL rides background merges (expensive at volume) → **ttl_only_drop_parts=1** (drop whole parts; needs time-clustered data) or PARTITION BY toStartOfWeek(Timestamp). TTL with WHERE (keep errors longer), per column, GROUP BY downsampling.
- **Scale vertically before sharding** (no JVM limits; network is the slowest part). HA ≠ horizontal scaling.
- **Replication**: ReplicatedMergeTree + **Keeper** (Raft-based ZooKeeper replacement; same binary). Active-active; state = parts + metadata; operations: inserts (add parts), merges, mutations/DDL; recorded in global replication log in Keeper (typical **3-node ensemble**); asynchronously replayed → **eventual consistency**; **insert_quorum** for stronger guarantees (fails and removes block if quorum not met). Walkthrough: Node1 writes parts A,B → Node2 fetches A → Node3 fetches A,B, merges to C, logs merge → Node2 fetches B → Nodes 1,2 fetch C or merge themselves, delete A,B. Backups to object storage for cold start. **Parallel replicas** split a query across replicas.
- **Sharding**: shared-nothing; app picks shard or **Distributed table** (proxy) with sharding key (ServiceName, Region; unrelated to primary key) or random; queries fan out, local aggregation, initiator merges.
- **Single-region cluster**: 2 ClickHouse nodes (ReplicatedMergeTree) + 3 Keeper replicas on separate nodes; LB writes. **32 cores / 128 GB RAM ≈ 20 billion events/day, peak ~300–400k events/s; ~500k/s with LB across replicas**; near-linear scaling. Compression **10–20x**: **20 TB raw/day → 1–2 TB on disk**; two servers × 7.5 TB NVMe (full copy each) ≈ ≥3 days before object storage. Sub-second typical queries with good schema.
- **Multiregion** (Fig 14-16): each region ingests locally (latency, reliability, cost); Distributed table with **Region** sharding key for query routing; add region by extending Distributed definition; region outage → others still queryable; data stays in home region.
- **SharedMergeTree** (proprietary, ClickHouse Cloud): single shard on object storage, no data replication between nodes; replicas = extra compute; coordinate via Keeper; shared query execution; fast scale up/down, **scale to zero**; lightweight strong consistency for SELECT; cheaper storage; hundreds of replicas/table; "retention becomes a nonissue". Comparable to Retriever's stateless readers over object store.
- HyperDX: "had it existed, we would have built on it".
- Interview angles: explain MergeTree/granules/sparse index; how a query prunes; choose primary key; Map vs JSON vs materialized columns; skip index trade-offs; materialized view pipeline for error alerting; TTL design; replication vs sharding; size a cluster (events/day, compression); Retriever vs ClickHouse trade-offs (eager S3 + Lambda vs local-first; trace-only joins vs arbitrary joins/ASOF; many services vs single binary).

## Ch15 Cheap and Accurate Enough Sampling (read in full; code listings partly truncated in extraction but text explains each; figures 15-1..15-4 described in text)
**Argument:** Sampling keeps representative events with full context plus their sample rate, unlike metrics which collapse context. Progression: constant probability → volume-based dynamic → by key → key + recent volume → target rate → per-key target rate → head+tail per key. For traces, decisions must be consistent (shared sampling ID) and when the decision is made matters (head vs tail vs buffered at collector).

- Can't run observability infra as big as production. Most events are identical successes; keep representative "good" events to compare with "bad" ones, plus metadata to reconstruct. Sampling saves cost and cognitive load even at small scale.
- **Constant-probability**: keep 1 in N. Reconstruct by multiplying counts/sums by the rate (100,000 requests, 100 events kept → each represents ~1,000). **P99/median don't need adjusting under constant rate.** Fails when: errors matter more than successes; some customers send orders of magnitude more traffic; traffic surges could overwhelm backend.
- **Recent-volume dynamic**: rate up when traffic low, down when surging; reconstruction needs **weighted** maths (count = sum of represented events). Median example: (value, rate) pairs {1,5},{3,2},{7,9} → naive median 3; expanded [1×5, 3×2, 7×9] → **median 7**.
- **By content/keys**: rates per key (HTTP status, method, request size, UA concatenations). Errors > successes; new orders > status checks; paying > free tier. Works when key space small and relative rates stable; plan for when assumptions reverse (error spike).
- **Per key + historical**: rate per key based on how often the key combo (e.g. [customer_id, dataset_id, error_code]) appeared in the **last 30 seconds**; frequent = less interesting.
- Choosing: front page app (90% identical) vs DB proxy (repeated query patterns) vs backend behind read-through cache (mostly unique).
- **Traces**: independent per-service decisions → broken traces. **Head-based** (decide at root using fields known at start: endpoint, customer ID; propagate a "guarantee sample retention" bit). Fields known only at end (status, latency) need **tail-based**: buffer all spans then decide; computationally expensive; not feasible inside instrumented code → **collector-side** logic.
- Go progression: base handler records every event → **fixed rate** (`rand.Float64() < 1/sampleRate`, flag 1000) → **record the sample rate in the event** (collector can't know when the rate changed; rates vary between and within services; multiply counts and duration sums by each event's rate, Figs 15-1/15-2) → **consistent sampling**: centrally generated sampling/trace ID propagated (book uses `Sampling-ID` and `Upstream-Sample-Rate` headers; W3C TraceContext specifies more rigorously); derive r from the ID instead of random per hop → traces kept/dropped whole; children with higher rates (Redis 1/1000 under parents 1/10) never orphaned → **target-rate**: track previous minute's request count, set rate to hit `targetEventsPerSec` (e.g. 5); rate can be a float → **multiple static rates**: baseline 1/1000, errors 1/1, slow 1/5 (but error spike → everything sampled) → **key + target rate**: outliers (latency > 500ms or error) get own budget (outlierEventsPerSec 1) vs ordinary (targetEventsPerSec 4) → **maps over arbitrarily many keys** (counts, sampleRates, targetRates; `neverSample(k)` for keep-alives/health checks) → library **dynsampler-go** (fair share per novel key; target-rate or no-target algorithms) → **head + tail per key**: parent passes head decision + rate to children, forcing sampling downstream; separate head/tail maps.
- Advanced: raise head-sample probability when downstream tail heuristic sees errors; **collector-side buffered sampling** combines head benefits with tail-known properties.
- OTel libraries increasingly implement this; still must understand mechanics to choose.
- Interview angles: why record sample rate per event; weighted median; consistent sampling via trace ID; head vs tail vs buffered; target-rate per key; when constant sampling fails; health-check exclusion.

## Ch16 Telemetry Management with Pipelines (read in full; Mike Kelly, Founder/CEO Bindplane; 7 figures described in text: stages, fan-out, components, deployment patterns, 3 adoption phases)
**Argument:** Treat telemetry flow as its own concern. A pipeline (built on OTel Collector + OpAMP) collects, normalizes/secures, enriches, reduces, routes, with resilience and a control plane. Agent+gateway is the standard pattern; adopt in phases (greenfield → redirect legacy agents → replace). Business case: ~50% ingest savings, ~10% reinvested, ~40% net; vendor neutrality; telemetry as strategic asset.

- Origin: Bindplane started as "monitoring integration as a service" before "telemetry pipeline" existed. Collecting everything → CFO questions. Classic scaling problem.
- **Power grid analogy**: substations, routing, redundancy; consumers just plug in.
- **Core functions / stages** (Fig 16-1): **collect → normalize (and secure) → enrich → reduce → route**, underpinned by **data resilience** and **pipeline control & observability**.
- Why now: cost + standardisation (OTel). Benefits: add tools without touching code; central compliance; reuse telemetry across observability, security, AI/ML, BI.
- **Collect**: OTel Collector; **>100 receivers** (OTLP, Prometheus, StatsD, JMX, host metrics). Move away from proprietary agents tied to one destination.
- **Normalize & secure**: parsing/coercion (unstructured → structured, fix timestamps, schemas); normalise formats (JSON logs, Zipkin traces) to **OTLP**; redact **PII**, access/retention/**residency** controls (**GDPR, FedRAMP**). Normalize early.
- **Enrich**: infra (k8s pod/node/region/AZ), business (customer ID, env, service tier), lookups (IP → geo, DNS → hostname).
- **Reduce**: filtering, deduplication, aggregation, sampling (head/tail/adaptive); central, adjustable in real time.
- **Route**: **fan-out** (logs → **SIEM**, metrics → APM, events → analytics, high-fidelity copies → cloud storage for compliance; Fig 16-2) and flexibility (test new tools without reinstrumenting).
- **Resilience**: buffers per stage + optional disk persistence; retries with **exponential backoff** and **backpressure** (avoid thundering herd/cascades); HA/failover of agents, gateways, control planes. Bindplane buffers locally, queues, failover paths.
- **Control plane**: real-time visibility (throughput, errors, latency of the pipeline), policy enforcement, runtime config management, incident response (**rehydrate** historical data, reroute, isolate), **fleet management** via **OpAMP (Open Agent Management Protocol)** (health, configs, updates); Bindplane adds versioned rollouts, remote upgrades, failover, rehydration.
- **Components**: **agents** (lightweight Collectors on hosts/containers/sidecars), **gateways** (centralised clusters for processing/compliance/reduction/routing), **control plane**. Collector architecture: **receivers** (HTTP, gRPC, Kafka, Syslog), **processors** (normalise, enrich, sample, batch), **exporters** (Prometheus, Elasticsearch, Datadog), **extensions** (zPages, health checks, auth). Same binary runs as agent or gateway.
- **Deployment patterns**: agent-only (simple, tight coupling, doesn't scale); **agent + gateway** (most common prod; decouples collection from delivery); **multi-tier** (local gateways → regional gateways; HA/DR/cost).
- Scale: customers processing **petabytes/day** across **hundreds of thousands** of collectors. Agents: minimal processing, CPU/memory limits, small buffers. Gateways: horizontal scale, redundancy, LB, buffering/queuing; health checks on queue depth, latency, error rate.
- **Build vs buy** (Table 16-1): open source/DIY (flexibility, no lock-in; high ops burden, expertise), vendor supported (fast, low ops; constrained, lock-in, licensing), **hybrid** (OTel + OpAMP + commercial control plane like Bindplane; vendor-neutral with enterprise features; more complex; increasingly common). See ch29.
- Path: start agent+gateway day one → add control plane → multi-tier regional.
- **Adoption phases**: (1) greenfield app/service end-to-end (Fig 16-5); (2) **redirect existing agents** to gateways for central compliance/reduction (Fig 16-6); (3) **replace legacy agents** with OTel Collectors (Fig 16-7). Fragile legacy apps may stay in phase 2 forever. Practices: don't boil the ocean (highest-value streams first); communicate trade-offs; run old and new side by side (rollback path); invest in education/culture. Rarely need to reinstrument everything.
- **Case data**: **40% of SIEM ingest never queried** (one case); fleets of **25,000+ collectors** with drift/config errors. Collect (versioned fleet-wide configs, validation, live status) + reduce (drop high-churn fields, collapse duplicates, sample noisy sources, redact; archive to GCS/S3). **Costs drop ≥50%**; one customer eliminated a **$2.6M overage**, ~**$2M savings**.
- **Business case**: ingest-based pricing; **20–40% of SIEM data never queried** (common finding); cost **predictability** (explain 30% spike → forecastable invoice); vendor neutrality = negotiating power; telemetry as raw material for observability, security, compliance (**GDPR, FedRAMP, HIPAA** redaction before leaving environment). Economics: **save ≥50% → reinvest ~10% → ~40% net**.
- Interview angles: design a telemetry pipeline (stages, agent/gateway, buffering, backpressure); migrate from proprietary agents; where to redact PII; OpAMP; ROI arithmetic; SIEM cost reduction.

## Ch17 Ontologies as a Shared Language for Humans and AI (read in full; Frank Chen, CTO Balto Energy & Designer-in-Residence UCSD Design Lab; 3 figures described in text)
**Argument:** Many failures are **semantic**, not infrastructural: infra dashboards green while business is wrong. An ontology (entities, relationships, rules) made operational through semantic conventions gives humans and AI shared meaning. Define nouns and invariants, glue with provenance metadata, schematize AI intent (ActionPlan), validate in CI with three gates, emit the same payload in prod (signal parity), and use the "AI sandwich" (deterministic → AI → deterministic validation). Close the loop: prod failures become golden-dialog tests.

- Opening: 2 a.m. Saturday; infra dashboard "99.9% uptime, <200ms, 200 OK"; business dashboard: bills curtailing solar exports instead of crediting; AI agent hallucinating price windows. "Availability" means server up (dev) / low latency (SRE) / accurate bill (business) (Fig 17-1 fragmented "reliability").
- Ontology = formal explicit specification of shared concepts and relationships; not academic knowledge graphs; a map of core objects, relationships, rules used as a layer in org and observability data. Payoff: fewer alerts, faster diagnosis, dev-to-prod signal match, guardrails for AI.
- Implemented via **semantic conventions** = translation layer (business: cost/usage; engineers: tie latency/throughput to business processes; system: rigid schemas). Frameworks: **Palantir Foundry, Apache Jena, Apache Atlas, OpenMetadata**.
- Running example: energy management system pricing bills from usage under shifting utility tariffs + AI agent proposing optimisations.
- **Nouns**: **IntervalSeries** (input: timestamped usage), **Tariff** (deterministic ruleset: time-of-use windows/rates for a period), **BillSet** (output = Tariff applied to IntervalSeries), **ActionPlan** (AI's structured interpretation of intent; untrusted until validated).
- **Invariants**: **Coverage** (every timestamp maps to exactly one pricing window; no gaps/overlaps; pricing_coverage), **Arithmetic** (total_cost = sum of components ±$0.01), **Determinism** (same series_id + tariff_id → same determinism_hash every time). Invariants as runtime assertions = **"semantic firewall"**: can't unit-test every hallucination (infinite inputs) so constrain outputs; simulate ActionPlan and reject if invariants break.
- Graph (Fig 17-2): IntervalSeries (physical truth) + Tariff (logic) → BillSet (financial truth); ActionPlan sits outside as proposed modifier (shift consumption or switch tariff).
- UCSD Design Lab **Agile Electrification** group open-source playbooks (DERs, parsing NL intent into ActionPlans, energy ontology).
- **Provenance metadata**: IntervalSeries lineage {source: smart_meter_api, fetched}; Tariff {tariff_id, rules type time_of_use, windows, **ruleset_version** "2025.12.1"}; BillSet links input_series_id + applied_tariff_id. Rules: map every output to input series_id; version logic; embed lineage. → cost spikes correlate to logic/input changes automatically.
- **ActionPlan schema**: plan_id, status PROPOSED, predicted {bill_delta_usd: -94.50}, actions [{device ev_charging, time_shift 22:00–06:00}], lineage. Converts "vibes" into measurable fields.
- **CI as contract** (shift left): immutable fixtures (golden path + edge cases). **Three gates**: (1) **deterministic** (hash stable, arithmetic, coverage; binary pass/fail); (2) **simulation** (run ActionPlan through engine; confirm predicted savings within tolerance); (3) **semantic** (golden dialogs scoring explanations; **confidence floor e.g. 0.6**). Ch21 for evals. Workflow: structural fail → fix schema; coverage → logic mapping; semantic → prompt/retrieval. Emit same JSON in CI as prod: "fixing the build" = "fixing the system".
- **Signal parity in CD**: dashboards hang off ontology objects; the assertion blocking a PR = the query that pages in prod.
- **Hierarchy of signals**: structural integrity (pricing coverage, tariff effective dates), logic stability (bill anomalies vs baselines or "twin" simulations; **ranking drift**: different tariff recommended for same usage), AI reliability (**proposal acceptance rate**, **eval pass rate**, fuzzy-match vs golden dialogs, user rejections).
- **Universal payload**: home_id, series_id, tariff_id, ruleset_version (usage change vs rule deploy?), pricing_coverage, determinism_hash, which invariant violated; AI: model_name, prompt_version.
- **AI sandwich architecture** (Fig 17-3): separate "physics" (deterministic workflow: legal precision, invariant enforcement) from "imagination" (dynamic AI workflow: ActionPlan as intent capture). Never execute AI proposals directly: AI output = hypothesis; rules engine = test (valid BillSet? savings confirmed? constraints held?). **Proposal-rejection rate = highest-fidelity AI reliability signal.**
- **Close the loop**: rejected proposals → capture prompt, IntervalSeries, Tariff → scrub PII → promote to **golden dialog** in CI → block deploys until model passes (e.g. leap-year tariff change). **Eval pass rate as an SLI**; a drop is an incident like a latency spike. Data flywheel.
- Scenario A (deterministic comparison): bind IntervalSeries, fetch 3 candidate Tariffs, 3 BillSets, coverage check, rank by total_cost; logs determinism_hash + ruleset_version → replayable audit trail.
- Scenario B (AI proposal "save me money"): ActionPlan shift EV charging to 10 p.m. → build counterfactual IntervalSeries → deterministic cost → AI predicted $20 vs engine $0.50 → reject as hallucination; log `proposal_status=rejected`, `rejection_reason=simulation_mismatch`.
- Conclusion: model input and output as untrusted; validate with rules-based invariants; turn 2 a.m. hunt into directed search.
- Interview angles: semantic vs infrastructure failure; define an ontology for a domain; invariants as runtime assertions; AI sandwich; proposal rejection rate; eval pass rate as SLI; signal parity CI↔prod.

## Ch18 Observability for CI/CD Pipelines (read in full; Hugo Santos, CEO Namespace Labs & Liz Fong-Jones, Technical Fellow Honeycomb; no figures)
**Argument:** CI/CD is a production system for developer feedback; build observability has the best ROI of any observability application. Map workflows/jobs/steps to traces/spans, define CI SLIs (end-to-end time, flake rate), find the critical path in the DAG, experiment to find real bottlenecks, measure P50 vs P90 (retries tax the tail), lean on toolchain incrementality. Honeycomb case: keep builds < 7 minutes using Docker Bake + BuildKit OTel traces.

- Observability and controllability are duals: slow feedback (Mars rover) makes fast analysis pointless. **CI** = source → build artifact; **CD** = roll artifact to production.
- xkcd "my code's compiling"; flaky test passes on rerun → folklore "safe to ignore".
- **Best ROI**: prod requests worth fractions of a penny; every CI request has a developer waiting (tens of dollars compute + hundreds of dollars dev time). Volume bounded (~**a dozen PRs per developer per day** max even with AI) → fits self-hosted OSS or free tiers; great place to start observability.
- **Ontology**: GitHub Actions (workflows, jobs, steps); Buildkite (pipelines, builds, jobs, steps); Argo/Concourse (applications, projects, states). Mapping: **workflow = trace; job = spans under workflow root; step = span within job**; step logs. Developers control execution (test/build jobs); platform teams control orchestration (batch PRs and split on failure; conditional tests by changed code) — start simple.
- **Instrumentation basics**: export job start/end/success; attributes: **repository and branch** (main vs PR branch: one slow test on a PR hurts one dev; merged to main hurts everyone). Emit at first/last step. GitHub Actions: OTel action exporting job/step durations.
- **SLIs**: success rate and latency → implicit SLOs; detect regressions; data instead of "feel" ("job duration has been degrading"). Performance = **end-to-end user time** until change validated. Also track **flake %** (successful retries), **test failure rate on main** (presubmit hooks working?), resource usage vs CI provider commitments.
- **DAGs**: prebuild container image job → dependency; failure blocks downstream (and their data). Visualise workflow as a trace to find the **critical path** ("only place optimisation yields faster feedback").
- **Pipelining/parallelism**: React frontend + Go backend + Rust backend; Go team says builds slower (bigger library) but **Rust dominates** → overall unchanged; optimising Go wouldn't help.
- **CI is production on a deadline**: CPU, memory, IOPS, I/O; correlate traces with host metrics/logs; experiment. Examples: (1) more cores didn't help JS build: **webpack** without **ThreadLoaders** single-threaded; (2) Go build **halved** with more cores (Go parallelism elastic); (3) fast incremental builds but slow releases: pushing images to all regions from one job → **network-bandwidth** constrained.
- **Predictability**: deterministic inputs → cacheable outputs (pulling an image by digest = correctness contract). Packing more jobs → contention → flakes → "does your culture tolerate flakes?" Resource flakes = **tail-latency tax**; compare **P90 vs P50**. go test scales across cores; browser E2E constrained by memory/I/O/external services. **Ephemeral dedicated runners** look pricier but cheaper after retries/investigation/wait time. Failures scale with fan-out (more engineers, coding agents). Real vs infra failure? Timing bugs surface when hardware gets faster. Robust tests to timing variance → higher packing ratios. Instrument OS limits: file descriptors, kernel shared memory, socket buffers; **cgroup metrics** for containers in integration tests.
- **Incrementality**: "5 min on my MacBook, 20 min in CI". Reproducible from-scratch is good but expensive; use toolchain caches (Go module + build caches) persisted between runs → isolation + speed.
- **Retries**: job failing 5% → enable retries → failures vanish but tail latency shoots up (P50 flat, sometimes 2x wait). Tests are your first representation of production; flake may be a real bug.
- **Honeycomb case**: target <**15 min**; internal SLO alerts if **>5% of builds exceed 15 min**. But devs task-switch at 15; **under 6–7 minutes** they stay and watch. Build system is mission-critical ("undeployed code is perishable"). **June 2018 → May 2019 median build doubled 7 → ~14 min** → switched CI provider for better parallelism; SLOs prevent "boil the frog". **2020→2025: 10–20 PRs/week to main → 100+/week**; LOC ~doubled; **Amdahl's law** (serial steps dominate even with infinite parallelism). **CircleCI buildevents** traces: tests fast; binary build + artifact upload slow. ~**3.5 GB** passed between steps, **gzipped not zstd**. Containers/k8s made stripped binary tarballs in S3 and binaries in ECR images unnecessary → build in one step. Omnibus serial step inefficient → **Docker Bake** (introduced 2019, popular ~2022) for chained multistep builds; interleaved parallel builds on one VM. CircleCI **Docker layer caching** slower than rebuilding or explicit cached base tarballs. Moved to single Docker Bake on CircleCI **machine executor** → established floor; balanced test sharding parallelism; Go integration test DB init became worth optimising. **Puppeteer** apt deps: high variance → cache apt lists/.deb from day's first run. **BuildKit has native OTel**: set **TRACEPARENT** to buildevents trace/span → see each command, ECR upload, blocking. Result: builds consistently **< 7 minutes**; compounding with AI PR volume ("validate code as fast as a model spits it out").
- **How-to**: top-level step durations first; OTel now best (Honeycomb's legacy buildevents). **GitHub Actions**: Collector receiver pulling via GitHub API key, or Actions add-on with OTLP destination. **Buildkite** exports OTel natively. **otel-cli**: `otel-cli exec --name "span" cmd`; nested via env vars / file; serialize state manually across machines. Docker: **DOCKER_CLI_OTEL_EXPORTER_OTLP_ENDPOINT** (don't also wrap with otel-cli → duplicates). Custom attributes: output sizes, cached data amount, module cache hit, count of files using legacy patterns.
- Interview angles: why CI observability first; map CI to traces; critical path + Amdahl; P50 vs P90 and retries; flake rate SLI; diagnose slow build (cores vs I/O vs network); Honeycomb 7-minute story.

## Ch19 Observability for Mobile and Frontend (read in full in two passes; Hanson Ho, Android Architect at Embrace; section by Matt Klein, CTO bitdrift; no figures)
**Argument:** Frontend/mobile observability happens "beyond the fence in hostile territory": you inherit the environment. Status quo = crash reporting, RUM, aggregated metrics, synthetic benchmarks, separate product analytics — "good enough" complacency. Hard because workflows aren't auto-instrumentable, context is restricted, delivery is unreliable (and loss is biased toward bad conditions). Klein: local circular-buffer storage + real-time control plane ("fidelity dial"). Ho: make observability **user-focused**: measure intention → outcome (e.g. checkout completion rate), detect user impact first, then find app causes.

- Backend controlled (known OS, resources, networks, time sync) vs mobile/web inherited (thousands of devices, OS/browser versions, cellular, throttling, captive portals, ad blockers, concurrent processes); must protect device performance, bandwidth, privacy, cost.
- Status quo: **RUM**, error tracking, crash reporting; client-side aggregation into daily crash rate, **time to first paint**; slicing limited to locale, app/OS version. Uses: surface/quantify problems + help reproduce locally (need code knowledge). Unlike distributed systems, problems reproducible on a single device.
- Example: NPE crashes in view-tree traversal across screens; RUM sessions show click on a button whose label has **non-ASCII characters** → code assumption → reproduce.
- Performance tracked via **synthetic benchmarks** in CI (Android **macrobenchmarks**): control hardware/device state → detect small significant changes; coverage only as good as benchmarked workflows.
- **Product analytics** (DAU for PMs) vs RUM model same behaviour but different datasets/vendors → "irate PM: key metric dropped, all our dashboards green".
- Limitations: noisy; need runtime factors as metadata; only static easy metadata captured; hard ones (network strength, ephemeral UX) missing. **1% of users 2x slower may not move P50 or P99**; at **100M DAU that's 1M people**. Many workflows never instrumented (only crashes, startup, network). Bespoke workflows need bespoke instrumentation; rare on mobile/web → vicious cycle. Impact assessment: "P75 startup +20%?" "P50 +80% but only Android ≤12?" User tolerance varies (mandated workplace app vs switch to competitor). Need correlation with DAU/revenue.
- **Domain challenges**: (1) complacency / curse of "good enough": devs want diagnostics for known problems, rely on CI benchmarks under unrealistic repeatable conditions (feature not bug), mobile on-call = master triager; don't expect root cause from prod data. (2) **Architecture**: no auto-instrumentable request→response summary; nonlinear usage; success = user got what they wanted, not duration (10 minutes on a screen tells nothing). Workflows span modules/teams, threads, screens with no shared execution context → "stop whatever span is active on this thread" fails; instrumentation complexity grows with coverage. (3) **Chaotic sandbox**: limited access to system resources/context (multitenant privacy) e.g. can't see concurrent YouTube video; telemetry delivery over spotty networks; **app least able to send telemetry when struggling** (GC pressure, user force-quits) → **loss skewed toward bad situations** → false sense of security unless you quantify data loss.
- **Matt Klein (bitdrift)**: mobile = "final frontier". Mature apps **>99.9% crash-free sessions** → non-crash issues (bugs, hangs, rage taps, rage quits) are higher leverage. "**99.99% at the server edge means little when malformed JSON in a 200 OK breaks the golden flow.**" Difficulties: **long release cycles** (weeks to roll out a log, months/years to reach all users); **users care about data usage** (metered plans; bandwidth contention hurts perceived performance and conversion); **sporadic connectivity** is normal; **unplanned termination** is the norm; **huge cardinality and cost** (small backend serves millions of MAU); naive local storage can block the **main/UI thread**.
  - Two competing goals: log as much as possible before shipping vs can't ingest everything from hundreds of millions of devices. Solution: **local storage** (high-performance **circular buffer**, persisted to disk; logs don't leave device by default; survives termination; minimal main-thread impact) + **real-time control plane** (bidirectional streaming; server tells device what to send under which conditions) = **"fidelity dial"**.
  - Monitoring: synthetic **counters/histograms derived on device** and sent compressed; change without app deploys. Debugging: dump the whole buffer as **session replay** on conditions expressed as a **finite state machine** pushed from server ("user views checkout; if they leave or 15 s pass without checkout, increment counter and dump full session"). Target cohorts (geo + version + device model) or a single user (support). Built on wide events → journeys/replays derived on demand. Replace the "simple pipe".
- **What to observe**: many simple systems, not one complex one; surveying a heterogeneous population; insights qualified by cohort context. P50 says little about P99 on mobile (cold start P50 1s vs 10s on a 9-year-old device). Discovery needs breadth (find small cohorts); diagnosis needs depth (often local reproduction). Android system profiling sees all processes, CPU scheduling, memory, hardware states — apps can't access it and data too big → local tools. Dual primary goals: **discover non-obvious issues** and **pinpoint reproducible conditions**; diagnostics secondary.
- **User-focused observability**: users as untapped data source; backend can't see why a 2-minute gap between requests. Quantify UX not with vendor "scores" or sentiment but **intention → outcome** events: happiness ≈ likelihood a user who expresses intention achieves a positive outcome. e.g. **checkout completion rate = completed checkouts / checkout attempts**. Differs from product analytics by being tied to performance/UX telemetry and context. **Flip the paradigm: detect user impact first, then app anomalies** (no more debating whether P75 +20% matters).
- Iterative analysis: filter by dimensions until cohort differences are statistically significant; expect false positives (cyclical usage).
- **FakeBurger** (fictional, tens of millions DAU): checkout rate = start_checkout and end_checkout linked by unique ID (first recordable without the second; log/logs/span). Passive context: sessionId, userId, app version; checkout-specific: payment type, discount code, **previous screen** (app-only concept invisible to backend); RUM navigation/taps. Compare new version vs rest, and vs previous rollouts; bias: **early adopters have better phones** → higher checkout rates. Questions: outsized cohort? other metrics changed? before/after differences in failed-checkout sessions? Found: "Next" button rendered below the fold; **new discount code format disabled Submit on first entry** (fixed only by re-entering; possibly no app release involved); rare serious errors hitting heavy users; many small glitches accumulating.
- Interview angles: why backend observability patterns fail on mobile; telemetry loss bias; circular buffer + control plane design; user-focused SLI (checkout completion); cohort analysis and adoption bias; RUM vs product analytics silo.

## Ch20 Performance Engineering with Observability (read in full; figs 20-1..20-5 described in text: flame graph, k8s heatmaps, per-service CPU, protobuf→JSON serialization profile, AST nodes)
**Argument:** Mature observability underpins performance engineering (faster, cheaper). Choose compute purchasing models with observability data, squeeze fleets to SLO limits, test newest hardware/Arm, optimise Kubernetes bin-packing and serverless cold starts, ingest cloud bills as wide events, use tracing for the forest and profiling for the tree rings, ideally linked per span/customer. Continuous practice with compounding gains.

- **Honeycomb Dec 2021 bug**: LB latency vs app auto-instrumented spans disagreed for single-event POST ingest (server tenths of ms vs LB single-digit ms). Ruled out tracing overhead using Go **net/http/pprof** + `go tool pprof` flame graph (Fig 20-1): **regexp.Compile = 17% of CPU** → HTTP router (mux) rebuilt for every request instead of singleton. **Five-line fix** (initializeRouter() in Start()). Tracing couldn't catch it because tracing hook runs after the mux is instantiated.
- Performance engineers historically used separate tooling; aim: unified observability from assembly instructions to user journey. **Brendan Gregg**: *BPF Performance Tools* (2019), *Systems Performance* (2020).
- **Practice**: two needs: lower cost, faster UX. Baseline before experiments; quantify (latency, data size, dollars, CO2). Avoid premature optimisation where salary/opportunity cost > gain; but guardrails against waste. Honeycomb invested: high cloud bill relative to headcount; SaaS gross margins. Same ODD loop: find impactful change, instrument, change, inspect. No separate perf team; make it continuous.
- **Six compute purchasing models**: capex (own DC, e.g. **Oxide Computer**); reserved capacity (AWS/Azure savings plans, Google committed/sustained use); persistent defined (EC2, Azure VMs, GCE); interruptible defined (**Spot**, Azure Spot, Google Preemptible); persistent elastic (**Fargate**, Azure Container Apps, **Cloud Run**); interruptible flexible short requests (**Lambda**, Azure Functions, Cloud Functions). FaaS: perfect utilisation, higher unit cost, cold starts. VMs: warm caches/connections but idle cost. Bare metal: cheapest CPU-hour, capex + ops. Containers orthogonal. Mix: DBs on VMs (RDS/Cloud SQL), frontends serverless, workers Fargate/Cloud Run. Spiky + Lambda can be costly/cold-start heavy; OK if Lambda time ∝ revenue. Serverless span duration → **"request cost"** attribute. Concurrent span counts → provisioned concurrency; sustained utilisation → move to server-ful.
- **Fleet-wide**: squeeze (fewer tasks, smaller allocations, higher autoscaling targets until SLO/tail degrades), optimise, migrate architectures. Old rule: **Intel SMT ~40% utilisation; Arm / SMT-off 70–80%** — retest on current cores until latency degrades. Always test newest hardware gen. CPU:RAM:storage ratios; high-RAM premium; **EBS** costs; NVMe instance storage (AWS -d suffix / i- prefix, Azure L-series) for I/O-bound. Fleet-wide profiling finds shared library/kernel hotspots: 1% of 1% not worth it, but 1% across all workloads is (**Google-Wide Profiling**, Ren et al. IEEE Micro 2010). **Arm64**: AWS **Graviton**, Microsoft **Cobalt**, Google **Axion**; ~**30% price-performance gain per generation**; switch base images, test build pipeline, representative traffic, load test to saturation; run Arm hotter (no SMT contention).
- **Kubernetes**: bin-pack mismatched CPU/RAM workloads. Interruptible instances if stateless and tolerant of ~**2-minute lame duck**; **Karpenter** + **Node Termination Handler**. Observe with OTel Collector **DaemonSet** + **kubeletstats receiver** + **k8sattributes processor**. **Heatmaps over percentiles** for node/pod saturation ("clipping" 100% CPU; Fig 20-2); find hotspots/undersaturation by node group, instance type, arch, AZ. Ingest **Cluster Autoscaler / Karpenter** logs to see scaling decisions. Shrink boot volumes. Sum CPU/memory by service/DaemonSet (Fig 20-3): "saving 1% of 10% beats 5% of 1%". Key metrics: pod CPU utilisation, memory requests/limits. Pitfall: rollout surge and pods starting/ending in the window can **double apparent pod count** → plot per configuration template hash. Reserved vs used; overhead DaemonSets (Lacework, OTel collectors, node-local-dns, kube-proxy, CSI drivers) add up across hundreds of hosts. **Bin-packing maths**: 32-core node with 20-core pods wastes **11–12 cores** (DaemonSets ≤1 vCPU) → use 64-core nodes (three 20-vCPU pods) or 15-vCPU pods; avoid stranding CPU or memory.
- **Serverless**: billed for duration, startup/cold starts, CPU/RAM size, API calls. CloudWatch concurrent executions, invocations, duration. **Lambda Power Tuner** (minimise CPU × duration). **Cold start billed** (init work): instrument init span (start of main → setup done), "running" span per invocation, "sleeping" span from freeze to thaw. **S3 reads ≈ 25% of Retriever's serverless cost.** **Provisioned concurrency = "worst of all worlds"** (manual capacity planning, no real discount, no amortised setup).
- **Observing costs**: faster execution almost always cuts cost most. Dimensions beyond time (instance type/size; network; storage). **Ingest the cloud cost and usage report as wide events** (cost field, service, usage type, each tag a column) → chargeback per tenant. Savings plans sized from minimum hourly spend. LB, **NAT gateway**, cross-AZ data transfer costs → keep traffic in-AZ; network can exceed compute+storage.
- **Application observability for cost**: span major functionality; account for time to nearest **100 ms**; long spans with no children = "mystery-meat time" → add subspans. Don't span every function (overhead); aggregate to tens of ms; use profiling below that.
- **Profiling**: interrupt with OS signals, record program counter + stack into ring buffer, count; symbolize; sample ~every **10 ms** (1 ms overkill); statistical. Go: built-in pprof HTTP handler on a **non-internet-visible port**; curl during behaviour; `go tool pprof -http :8080`; supply source and binary; `go test -bench` with CPU profile. Java: **Java Flight Recorder (JFR)**; else Linux **perf** or eBPF agent. Prefer **flame graphs** over source listings/DAG: width = time incl. children; stacking = calls; shows most expensive code, code vs libraries, self vs children. Best targets: often-called medium-cost functions (library called from 10 places) or near-root functions with little child time.
- **Continuous profiling**: agents or scrape endpoints; minute profile ~**5 MB** but 2 hours ≠ 120x (redundant, compresses). Tools: **Grafana Pyroscope, Polar Signals, zymtrace**; OTel common profiling agent/SDK/encoding.
- **Signals together**: tracing = bird's-eye/forest; profiling = microscope/tree rings. Questions: is endpoint normally slow? query slow only for this endpoint? always this DB call? Changes can show in profiles not traces or vice versa. **Profiles indexed per second or tied to spans** → what, for whom, why, how. Day-2 value persists (new services, new bugs).
- **Golden example**: serializing a complex query with nested derived columns **protobuf→JSON for every Lambda invocation** (hundreds of thousands) on one hot Retriever merge node (Fig 20-4) → cache serialized JSON. Same user's query slow on Lambda due to many AST nodes from deeply nested **if/else** chains → added a **switch** statement to query language (Fig 20-5). Found via per-customer high-cardinality profiling, invisible to traces.
- Conclusion: diminishing returns at top; compounding 0.5–2% gains; loop measure → improve → measure. Late 2024: half a dozen teams wanted input on continuous profiling tool; finance+engineering cost modelling from AWS bill + app + k8s telemetry.
- Interview angles: tracing vs profiling; flame graph reading; regexp/router bug story; compute model selection; k8s cost visibility pitfalls; bin-packing arithmetic; serverless cold-start cost instrumentation; cloud bill as wide events; Arm migration.

## Ch21 Observability for Large Language Models (read in full; Phillip Carter principal contributor; Fig 21-1 eval loop described)
**Argument:** LLM apps are opaque, nondeterministic, and fast-changing, and latency is a poor UX proxy. Use evals (pass/fail/maybe) together with telemetry in a flywheel: production traces → evals → harness/prompt fixes → telemetry. Follow OTel GenAI semantic conventions; decide input/output visibility, cost derivation, user-feedback attributes; SLOs for upstream providers; fix with code (harness) as well as prompts.

- LLMs lowered the barrier to "anyone with a credit card". Opacity: no debugger; **temperature/top_p** don't guarantee repeatability; input space impossibly broad; adversarial users. 2025 leapfrogging via harnesses/tool calling; behaviour changed by prompts, not just code.
- Classic UX proxies: **Apdex**; **Greg Linden 2006: Amazon lost substantial revenue per 100 ms added**; **Google 2006: +0.5 s latency → 20% traffic drop**. For AI, **time to first token** useful but fast wrong answers don't satisfy; in agents a failed sub-operation (fetch a page, bad API params) matters less than whether the overall task completed. GPU/token cost is a discrete cost component.
- Mirrors distributed systems tenets: expect failure, distrust dependencies, everything has a price → instrument.
- **Evals**: like unit/integration tests but results **pass, fail, maybe**. Honeycomb **Canvas** (AI chat that calls tools to query telemetry): **question evals** (facts from **golden data** query results; **task function** generates output; **scoring function** = string match against known values) and **task evals** (fuzzy investigations/root cause; score the **steps taken**; need workflow telemetry; Fig 21-1 loop). Use evals to compare new model versions, replay sessions against prompt/harness changes. Great evals can coexist with terrible UX → observability fills gap.
- **Telemetry design**: auto-instrumentation in LLM client libraries; **OTel generative AI semantic conventions** (token counts in/out, model name, sampling params, system prompts on client spans). Questions: (1) **input/output visibility**: large/varied; store in system of record and **link** from an attribute; elide binaries (images, PDFs); privacy/regulation; users use poor discretion. (2) **promote traces to evals** easily (many eval frameworks support OTel). (3) **cost**: no standard semconv cost key → **derive cost at query time** from model + tokens (recommended; compare prompt versions/models). (4) **user feedback** attributes (thumbs up/down, user retry).
- Agent pattern: LLM calling tools in a loop, touching auth, DBs, history, knowledge bases, remote APIs → telemetry must connect AI part to the rest of the system.
- **Analysis**: two outcomes: deterministic parts working (multidimensional analysis; upstream provider **rate limiting, retries, response time**) and continuous improvement loop for nondeterministic parts. **Token/prompt caching** (provider discounts) → put cache info from API responses on spans to find missed caching or bad invalidation. Provider timeouts/failures → **SLOs not threshold alerts** (nothing actionable unless you are the inference provider).
- **Honeycomb MCP server**: can't see caller's reasoning, only actions; instrumented tools usage/failures; **SLO 90% query success**. Findings: calling models **jumped to conclusions about field names** even when told to check fields first; struggled to **interpret/modify time ranges** → new eval classes, prompt and tool-description iteration.
- **Harness** = deterministic code around the model (tools, input/output correction, user comms). Must test in prod; decisions may not last 6 months.
- **Query Assistant**: launched with ~**25% error rate**; many JSON validation errors (e.g. `{"op":"COUNT","column":"exception.message"}` invalid because COUNT takes no column) → programmatic correction (drop column) → **25% → ~14%**; later prompt improvements → **<1%** (excl. timeouts). Insight: users actually wanted COUNT with a column → shipped syntax change, removed correction code.
- **Eval flywheel from traces** ("90% of the way" if you collect inputs/outputs/errors): for new inputs, decide if worth evaluating; is there an ideal output; correct it; grow golden dataset; prune unrepresentative items; rerun and compare history (expect a drop at first).
- Canvas task evals: steps to answer, tokens used, key conclusions; **LLM-as-a-Judge** pass/fail + regular **manual review** sample. Found **is_slow** calculated field (>500 ms) misread as a feature flag/load test → wild goose chase → adding a **description** fixed it. Common failure: models impute meaning.
- Public benchmarks (hallucination, toxicity, tone, truthfulness, bias) can mislead; app can score well and fail users.
- Interview angles: why latency isn't UX for LLMs; eval types and scoring; what to record on LLM spans (and what not); cost attribution; SLOs on providers; harness fixes vs prompt fixes (25%→14%→<1%); MCP server SLO learnings.

## Ch22 Fin's Case Study in Modern Engineering (read in full; Kesha Mykhailov, Staff Product Engineer at Fin (formerly Intercom); 12 figures described in text)
**Argument:** Tie every change to a customer-centric measurement and make it debuggable. Fin's journey: resolution rate as north star → customers complained of slowness → **time to first token** end-to-end signal → rebuild traces with low-level spans to find critical path → **eager requests** (−2 s median TTFT) → event-based latency SLO → finance found wasted LLM spend → **cost per interaction** on traces + SLO. Rasmussen model: observability surfaces the three boundaries.

- Fin = customer-service AI agent answering end-user questions for customers; conversation answered = **resolved**; **resolution rate** = key efficiency metric. Fin charges only for resolved conversations → **aligned incentives**. Launched **March 2023**; resolution rate up ~**1 percentage point per month** (Fig 22-1), averaged across all customers. Evolved from single LLM call to agentic system; **dozens of A/B tests** in prod, each a fraction of a point; capabilities prioritised over speed.
- **Early 2025** complaints Fin was slow. Fin built on Intercom platform; distributed system; "how do I activate my account?" triggers several background requests using LLMs at various speeds (Fig 22-2). **Hundreds of engineers, 20 teams**; ~**100 changes shipped per day** even on a Friday ("shipping is our heartbeat").
- Component optimisations showed improvements but customers unimpressed → lacked end-to-end signal → **time to first token** measured on the frontend (message submitted → first reply tokens rendered in Fin Messenger) (Fig 22-3). Engineers knew "what" not "why"; traces lacked detail.
- Naive trace picture: transactions end-to-start sequential (Fig 22-4); reality: agent work doesn't align with service transactions (Fig 22-5); couldn't tell what was on the **critical path** vs post-processing. Rebuilt traces with **low-level spans** marking where control passes between transactions (Fig 22-6).
- **Eager requests**: before LLM stage there's DB storage of messages, customer workflows, deciding if Fin engages; invoke LLM processing eagerly in parallel; if normal flow doesn't alter the prompt payload (majority), answer already ready (Fig 22-7) → **−2 seconds median TTFT**.
- Protect gains: model availability unpredictable (provider outages, daily seasonality, capacity) → threshold alarms noisy → **event-based SLO: % of interactions faster than new baseline** (Fig 22-8); watch long-term compliance trends.
- **Finance enters**: customers can route conversations straight to humans (e.g. sensitive payments) → eager LLM requests wasted; no Fin interaction → no latency metrics → invisible (Fig 22-9). Found by finance's **quarterly gross margin review**. Fixed via tracing; validated with finance's warehouse query of **LLM waste %** (Fig 22-10) — but that query takes minutes and warehouse refreshes daily (hours). Added **cost per interaction** to traces (Fig 22-11) + SLO on it.
- Empathy with customers (TTFT), business (cost per interaction ≈ cost per resolution, which is billed), engineers (detailed telemetry).
- **Rasmussen safety model** (Fig 22-12): drift toward failure within three boundaries: **acceptable performance** (customers sad), **economic failure** (profitability; gross margin promised to investors), **unacceptable workload** (engineers overloaded). Art of observability = surface the boundaries in real time; dataset combining a **customer-centric** and a **business-centric** signal, real-time, linked to low-level traces. "**Last mile of observability**"; otherwise observability is a cost center discussed only as logging-cluster cost. "In the age of AI, empathy is all you need."
- Interview angles: north-star metric design; end-to-end vs component metrics; critical path in async systems; speculative/eager execution trade-off (cost); SLO on latency baseline; cost per interaction as a telemetry attribute; Rasmussen boundaries.

## Ch23 Organizational Learning Speed Is Now Your Biggest Constraint: An Open Letter to CTOs (read in full; includes letter from Darragh Curran, CTO of Fin; no figures)
**Argument:** In the AI era the constraint is how fast the org can **validate, understand, and learn**, and the biggest drag is **sociotechnical debt**. Three debts: devs live in tests not reality; telemetry treated as infrastructure not product; developer tools never designed as products. AI (per DORA 2025) amplifies whatever you already are. Fix: measure observability's value by developer learning + delivery speed, build feedback loops, match tools to architecture, run observability as a platform product, treat product observability as investment.

- **Sociotechnical debt** = hidden accumulated cost of misalignment between social structures (culture, teams, processes) and technical systems (Tamburri & Di Nitto, WICSA 2015, "social debt"). Shows up as reduced speed, engagement, flexibility; "we'll fix it later" era is over.
- Three truths: delivery constrained by validation/understanding/learning not code writing; observability sets the baseline for learning speed; ops-era tools lack precision for engineers → heroics; wisdom not encoded = doesn't exist for AI.
- Letter: orgs change infrastructure faster than how they work. "AI doesn't eliminate the need for engineering discipline. It eliminates the excuses for not having it." AI makes mistakes faster too. "Intuition does not scale." Duct tape flies off at 10x/100x.
- Guiding principle: any debt preventing teams moving "swiftly and confidently" today blocks AI speed.
- **Boris Tane sidebar** ("The Software Development Lifecycle Is Dead", Feb 20 2026): agents absorb design review/code review/QA/sign-off; monitoring is last line of defense. Old SDLC wide loop: Requirements → Design → Code → Test → Review → Deploy → Monitor. New tight loop: **Intent. Build. Observe. Repeat.** No tickets/sprints/story points/PR queues/QA phase/release trains. What's left: **context**. "The new skill is context engineering. The new safety net is observability." Observability is the only gate that survives — but must shed static dashboards, siloed pillars, old habits.
- **Debt 1: devs live in tests, not reality.** DevOps aimed at dev↔prod feedback loop and failed: still build/test/merge and move on; only ops has prod in their loop (laggy, lossy, threshold-driven). Elite teams wire prod signals into daily dev (frequent deploys, short lead times, low change failure rate, fast recovery). Test: dev ships Friday — on Monday do they know latency/errors/user behaviour, or does a ticket arrive two weeks later?
- **Debt 2: telemetry as infrastructure, not product.** 2009 LAMP: $50k monitoring bill reasonable. Then microservices, containers, serverless, edge, multi-cloud. Orgs went **broad** (more tools/dashboards/alerts) not **deep**. Vendors rebranded. **Gartner reference customer: $50,000/yr monitoring in 2009 → $24 million/yr "observability" in 2024 = 48% YoY for 15 consecutive years.** Observability = **20–30% of infrastructure spend at most companies**. "Paying observability prices for monitoring outcomes." AI raises change rate → small granular failures (latency spikes, partial outages, edge errors, cost regressions, correctness drift) compound silently. Test: does incident resolution take **15 min if the rockstar is there, 45 if not**?
- **Debt 3: developer tools never designed as products.** Accumulated from infra side. "Add good telemetry" = maze (metric/log/trace/profile/error; counter/gauge/timer/histogram; cardinality; when did it ship; batched with what; where does it show up). **Platform engineering** = product/design thinking for internal devs, discovery, paved paths, defaults, standard libraries, guardrails. Failure modes: **platform as a project** (launch then move on) and **pure rebranding** of DevOps/infra team. Test: new hire (last 6 months) instruments a new service and shows prod behaviour without pinging three people on Slack?
- **DORA 2025**: AI amplifies existing behaviours — strong feedback loops compound advantage; heroics compound chaos. Delivery speed ≠ learning speed. Developer attention shifts to system-level reasoning, intent, impact, verification. Retention via empowerment. Short-term productivity boost for all; without validation it's reclaimed by regressions/incidents.
- **Turning the ship around**: decide how to measure value, what to build, who builds it. Measure observability **not** as operational cost center, not only customer/business impact, but by ability to accelerate **developer learning and delivery speed at the same time** (ch26).
- Feedback loops: deployments (did it work?), code review (safe/maintainable?), incidents (what assumptions were wrong?), product development (users getting value?). Observability = shared sensemaking layer; low cost of curiosity → compounding learning. Slow/expensive/expert-only observability → engineers stop looking; knowledge concentrates.
- **Three shifts**: (1) **match tools to architecture and workflows** (three pillars forces stitching IDs/timestamps; vendor matters less than functional fit); (2) **run observability as a platform, not infrastructure** (mission: effortless understanding; measure time to understanding, ease of investigation, adoption, post-deploy confidence; not uptime/data volume); (3) **treat product observability as investment** ("observability inherits the properties of the code you observe": cost-center code → cost-center observability; revenue code → investment).
- **Make it real**: institutionalise deploy → observe → learn (ch25); observability as internal platform product (ch28); align goals/spend to business outcomes. **Success measures**: median time from deploy to validated understanding of customer impact (MTTD/interpret); % of material incidents first found via internal telemetry vs customer reports; % of deploys with post-deploy outcome check completed within a window.
- **Darragh Curran (CTO, Fin)**: mission: end "Dear valued customer / ticket number 123 / do not reply". Loop: **do a thing, learn something, do the next thing**. "**Shipping is your company's heartbeat**" (written 13 years ago). Pivoted whole R&D to Fin; AI-first culture. Great engineers understand customers, production systems, how software is built/deployed — each harder with AI (probabilistic products; costly slow unreliable LLM dependencies; agents producing "sort-of-working" code). Bottleneck isn't shipping or writing code but **understanding**. "**If shipping is your heartbeat, understanding is your breathing.**"
- Interview angles (leadership/staff): sociotechnical debt examples; why observability budget ≠ capability; metrics to prove observability investment works; platform engineering anti-patterns; DORA AI amplifier; new SDLC loop.

## Ch24 Systems Thinking for Software Delivery (read in full; 8 figures are loop diagrams described in text)
**Argument:** Software delivery is a sociotechnical system. Jointly optimise social and technical (Trist). The strongest interventions change **information flows**; observability is an information flow that creates **feedback loops**. Amplifying loops (confidence, learning accumulation, system quality) become virtuous cycles or death spirals depending on whether the system can see well enough to self-correct; balancing loops (incident breadth, observability cost) need accurate signals to regulate. Partial feedback (lossy, laggy, unpredictable, wrong, missing) distorts. Meadows' leverage points; beware pushing the right lever the wrong way.

- **DORA 2025**: "successful AI adoption is a systems problem, not a tools problem" (p.4); control systems ("that's us") must speed up; need faster feedback loops (p.9).
- **Systems thinking**: interconnected wholes; relationships, patterns, feedback loops. **Sociotechnical system** (Fig 24-1): technology and human behaviour intertwined; people, structure, incentives, processes, constraints shape each other.
- **Trist principle** (Eric Trist 1981): jointly optimise social and technical systems. Common violation: managers/directors/VPs choose tools without engineers closest to problem. "Can't hire your way out; can't buy your way out (more tools)."
- **Donella Meadows** (*Thinking in Systems*, 2008): weakest interventions = budgets, metrics, locations (absorbed). Strongest = **information flows** (what people can see → decisions). Firefighting consumes energy without changing system. "Changing observability changes your underlying sociotechnical OS." No observability → no feedback loop.
- Feedback loop (Fig 24-2): actions influence outcomes which influence actions ("great team got great tools, or great tools made great team? both").
- **Amplifying/reinforcing/positive loop** (Fig 24-3; business calls it "flywheel"): snowball avalanche; virtuous cycles or death spirals; exponential effects. **Balancing/negative loop** (Fig 24-4): thermostat; stability.
- Small shifts trigger massive change when an amplifying loop has strained against a balancing loop ("straw that broke the camel's back"). **Talent exodus** example: years of dissatisfaction (arbitrary promotions, cancelled initiatives) held by inertia/golden handcuffs/tough market → one respected engineer quits and posts → half of seniors gone in three months.
- **Virtuous vs death spiral = ability to self-correct**. Monolith breakup example: with traces, the 8th service's cascading timeouts are seen → pause, invest in tooling/on-call training → resume. Without, they guess "better isolation", add 3 more services... two years later, unmaintainable, costly rewrite. Same intent.
- Core loops: deployment, code review, incidents, product development — each needs sensing, interpretation, response; observability = sense mechanism. Degraded sensing → slow down, batch, heavyweight approvals, workarounds.
- **Amplifying loops**: (1) **confidence loop** (good observability → deploy more → small batches → faster detection → lower MTTR → trust → more risk/speed; inverse: fear → infrequent big deploys → longer incidents → crawl); (2) **learning accumulation loop** (Figs 24-5/24-6: easy answers → more questions → better mental models → faster debugging → expertise compounds; inverse: stop asking, shallow pattern-matching, knowledge concentrates → institutional risk); (3) **system quality loop** (fix small anomalies → clean baseline → easier detection; inverse: "normally broken" state, noise masks new problems, firefighting trap).
- **Balancing loops**: (1) **incident involvement breadth**: mobs vs lone hero; with data, measure resolution time vs participation, learning spread vs coordination overhead (e.g. "engineers who shadow >3 incidents learn to resolve independently; more doesn't help"); roles, spectator modes, recordings. (2) **observability cost/usage regulation**: without "observability of observability" → cost explosion ("bill hit $2M/month — turn everything off!") then overcorrection, or anxiety-driven underinstrumentation (Fig 24-7). With it: "checkout generates 60% of trace volume but 10% of queries"; "dashboard query scans 500 GB per load, nobody looked in 3 months"; "adding user_id multiplied metric cardinality 10,000x"; "fraud team runs $5,000/month of queries but caught a $2M incident in 10 minutes"; per-team budgets (Fig 24-8). "You can't regulate what you can't measure."
- **Partial feedback distortions** (inconsistent observability can be worse than uniformly poor): **lossy** (error rate flat so assume fine; miss segment latency, swallowed errors, 0.5% edge case; double down on bad behaviour), **laggy** (ship Tuesday, complaint Friday, 40 changes later; bike with 30-second delayed steering), **unpredictable** (ingestion hiccups → stop investigating intermittent issues), **wrong** (false positives/negatives; engineers learn the system lies; route around with intuition), **missing/open-loop** (coin-flip deploys, superstitions like "don't deploy on Fridays", only catastrophic failures visible; driving with eyes closed). Degraded feedback makes you learn wrong lessons → ossification; amplifying degradation. Institutionalised workarounds: unrealistic test environments, change approval boards, stale runbooks, safe deployment windows, freezes = "theatrical safety" → org optimised for not breaking things vs making things better; "standing still is falling behind".
- **Meadows' 12 leverage points**, abbreviated subset high→low: **goals**, **self-organization** (agency/autonomy, not org charts), **rules** (guardrails), **information flows**, **amplifying loops** ("a system with an unchecked reinforcing loop ultimately will destroy itself", p.155), **balancing loops**. Observability can't compensate for lacking purpose, empowerment, or rules; but goals need good information.
- **Push the right lever the wrong way**: deploys are the right lever, but CABs, monthly release trains made shipping slower and more dangerous.
- Conclusion: observability is the only intervention that both turns amplifying loops virtuous and stabilises balancing loops.
- Interview angles: explain sociotechnical system; amplifying vs balancing loops with software examples; how observability prevents death spirals; observability cost governance; why "don't deploy on Fridays" is a symptom; Meadows' leverage points; CAB as wrong-direction push.

## Ch25 The Observability Landscape Through a Systems Lens (read in full; 9 loop figures described in text)
**Argument:** Choose observability by the feedback loop you need. Most orgs run a fast isolated **dev loop** (build → test → iterate → merge → move on) and a slow reactive **ops loop** (alert → investigate → fix); neither connects "I wrote this" to "I see what it did in prod". The value loop is build → deploy → observe → learn. Closing it is rare because tools haven't been worth the cognitive cost. Three pillars serve ops loops; unified storage serves developer learning. AI breaks the logjam. Decide which loop is your bottleneck; most orgs overspend on the "goalie".

- Category sprawl: monitoring + logs + APM blender; up to **a third of infrastructure spend** in some companies; data/AI/LLM observability labels; vendors claim same outcomes. Authors: "we're sorry."
- Organising principle: start with feedback loops and decisions they support.
- **Dev loop** (Fig 25-1): build, run tests, iterate, merge, move on; devs don't know when code deploys; only look at prod for bugs/incidents.
- **Ops loop** (Fig 25-2): alert → investigate → fix; reactive, threshold-triggered after impact is significant; often a customer complaint about something shipped days/weeks/months ago (Fig 25-3); lurking issues from compounding conditions (data volume → timeouts → thread pileup → alert) (Fig 25-4). Reliability is a small part of what developers need (adoption, drop-off, intent vs outcome).
- **Missing loop** (Fig 25-5): dev loop stops at merge, ops starts when something breaks. **Inner loop / outer loop** terminology. "What you learn when all your tests pass is that all your tests pass." "People are agents of chaos."
- **Value creation loop**: shipping = heartbeat (Fig 25-6); build → deploy → observe → learn (Fig 25-7). **Fin ships its Ruby monolith ~70 times/day; 8–15 minutes merge to full rollout.** Deploy without observing = open loop (Fig 25-8); waiting for alerts guarantees learning only about system-threatening problems.
- Closing the loop (Fig 25-9): production = chaos; even AI agents scanning the haystack are of limited use; but knowing what/when/where, a single weird request is findable. The person who wrote the code must see it, understand users' experience, improve. Can't close by another person watching, by aggregate dashboards, or by connecting to ops loop. **Track developer intent through to prod and validate with rich context + precise tools.** Precision example: "**compaction rate for long strings +5%, disk footprint −30% for requests with a specific build_id, flag combination, and test users on our 10% canary vs 90% baseline; return-code distribution unchanged**" vs "no spike in errors".
- **Why rare: economics of cognitive load**: not culture ("devs don't care") but tools not worth the effort → circular dependency (no precision data → not worth looking → don't look → tools don't improve). Old ways "worked well enough". AI provides technical breakthrough + competitive pressure + necessity (nondeterministic agents).
- **Three pillars model** = operational outcomes: infra with thousands of third-party components; cheap stash; dominates integrations; easy start; cost balloons from many copies; destroys relationships at write time; manual correlation and intuitive leaps; fine for bugs/incidents, not product quality/user behaviour.
- **Unified storage model** = developer learning: from BI + APM intersection; all signals as structured events in one columnar store; relationships preserved; high cardinality + dimensionality → precise questions. 30th field > previous 29 combined. "**Patrick Snuffleupagus**" vs "boy". Example: "all requests from mobile users in the EU with flag X that had errors in checkout". Struggles with operational infrastructure monitoring.
- **AI**: code nearly free; constraint shifted from "code producing" to **"code coherence"**; generation cheap, confidence not; code as a **cache**; most code brownfield or **blackfield** (chaotic brownfield, "dark cave without a light"); prod is the "sole tattered remnant of developer intent". Risk accumulates faster than resolved when software changes faster than understood. MCPs may bridge pillars (footnote: evidence suggests agents seek richer upstream data with connective tissue, not logs/metrics). Agents can check back hourly/daily/weekly for slow burns (memory leak, cache drift). Adversarial **"continuous review" agents** (flag leaks, check constraints). Needs unified structured high-context events.
- Both loops matter; lead with the right one: ops loops = safety net (infra health, aggregate health, SLOs), downstream/delayed; developer observability moves learning upstream (prevention vs cure).
- **Decision**: which loop is the bottleneck? Operational stability pain → three pillars (mature, robust). Delivery velocity / understanding product per customer → unified model. AI-generated code influx / transition to AI-written code / tracing agentic workflows → developer learning. Most orgs invested heavily in ops loops (diminishing returns once stable) and little in dev loops: "**blowing their wad on the goalie**" and not staffing the field. Vendors "not bound by technical accuracy in the sales process"; skip feature bake-offs until aligned.
- Interview angles: dev vs ops loops; inner/outer loop; why devs don't look at prod (cognitive load economics); three pillars vs unified (when each); precise validation example; goalie analogy; how AI changes the bottleneck.

## Ch26 The Business Case for Observability (read in full; no figures)
**Argument:** Start the business case by identifying which loop is the bottleneck (operational vs developer learning), not vendor features. Operational loops = cost center (uptime, faster incidents, avoided outages, less burnout). Developer learning loops = strategic investment with external (product differentiators, UX) and internal (velocity) measures. Observability inherits the properties of the code it observes. Report developer observability into engineering leadership; run it like a platform team.

- Quote (Charity Majors): **"Infrastructure: the code you have to run, in order to run the code you want to run."**
- Ops loops: downstream, delayed, threshold-based; "guardians of stability, last line of defense". Dev loops: upstream, prevention.
- **Fred Hebert** (Honeycomb SRE): "It's great that you're so good at firefighting, but maybe it's time to **read the fire codes**?" Firefighting identity → reactive improvement.
- **Operational business case**: improved uptime, faster incident response, savings from prevented outages, reduced burnout. Ops loop success = answer quickly: **what is happening, who is affected, what restores service fastest?** Both models support it; unified shines at outliers and connecting SLO violations to underlying requests.
- **Signs of operational breaking point**: customers find critical bugs first; minor incidents escalate to long outages; investigation backlog grows; more break/fix than features; low CSAT from unreproducible perf issues; features delayed by untangling service interactions; hesitation to ship AI-generated diffs nobody understands.
- **Four levers**: higher incremental revenue (uptime/performance); savings from faster response (MTTD, MTTR, query speed, less on-call, fewer rollbacks); savings from avoided incidents; savings from lower turnover.
- **Developer learning case**: questions like "Am I building the right product? How are users using it? What happened when I shipped that change?"; crosscutting (impact by cohort, outcomes by feature state, regressions by request path, behaviour under real load). Unified model makes learning routine; three pillars at high cost (manual correlation, experts, minute queries, hour-long investigations) → larger batches, guesswork.
- Research on developer productivity: **DORA, SPACE, DX** (footnote: each point on DX index ≈ X hours saved/dev/year), GitHub. Budgets already buy learning indirectly (CI/CD, test infra, flags, experimentation, progressive delivery, IDPs). Gains modest because tools don't close the loop: **chaos engineering without attribution = chaos; feature flags without validation = "trust-fall"; progressive delivery without precise cohort detection = slower pipeline**. Closed loop: change → observe → act.
- **Dual mandate**: **external measures** (customer outcomes) and **internal measures** (engineer outcomes).
  - External: list differentiators, mission, roadmap, critical path, SLOs, how you make money. **Honeycomb targets: query builder/boards queries < 5 s 85% of the time; deep-dive queries < 30 s 85%; data availability 99.95% queryable within 60 s; durability 99.99% of submitted data persisted.** Less precision for non-critical services. Latency economics: **Amazon: every 100 ms costs 1% in sales; Walmart: +2% conversions per second faster; Staples: +10% conversions from 1 s faster home page.** Finance-friendly terms: fully-loaded engineering cost, recovered capacity from less firefighting, faster time to market, reduced incident investigation labour, avoided wasted build cycles; use baselines + conservative assumptions. Instrumentation decisions are **product decisions**.
  - Sidebar "cost of not paying attention": **Instagram** from Burbn (location check-in → photos); **YouTube** started as video dating; **Twitter** from podcasting platform **Odeo**; **Slack** from a failed gaming company's internal chat. Follow what users do.
  - Internal: CI/CD, deploys, tests, agentic monitoring, specs, SLOs, sandboxes, visual tests, progressive delivery, flags → hundreds of ships/day vs weekly. Teams that can't finish a migration or understand a session can't validate agentic workflows. **Uncertainty is expensive**; responses (coordination, mitigation) add drag. "Can't hire your way out of a velocity problem caused by uncertainty" (coordination tax).
- **Cost center vs investment** sidebar: cost center = expenses without direct revenue (IT, HR, legal, finance, facilities, ops, infra); investment = spend now for compounding return. "**Cost centers get cut; investments get funded.**" Observability **inherits properties of the code observed**: infra observability = cost center; revenue app code observability = investment; delivery/validation tooling = force multiplier on salaries (largest expense). Managing all observability as cost center degrades the information channel (e.g. banning high-cardinality data).
- **Organisational changes**: **reporting structure**: developer observability rolls up to VP Eng/CTO/sometimes CPO, not infra/ops/IT. **Team structure**: run like platform engineering ("Prime Directive": build components unique to the company but shared across teams; user research; devs as customers; minimise cognitive load; auto-instrumentation feels like magic; easy right thing). Footnote: a team that maintains a big codebase is a software team; one operating a big service is an ops team — not a "platform team" by renaming. Worst outcome isn't wrong tool (recoverable) but spending without alignment on problem/success/loop.
- Interview angles: build a business case for observability; ops vs dev loop ROI levers; external/internal measures; cost center vs investment framing; where the observability team should report; latency→revenue stats.

## Ch27 Diagnosing Your Observability Investment (read in full; no figures)
**Argument:** Cost pressure is a prompt to diagnose whether you bought the right capabilities and get the right returns. Don't pay observability prices for monitoring outcomes. Distinguish operational vs developer loops, avoid the firefighting trap, separate activities from learning, track loop-specific indicators, and manage investment with diminishing returns caps, impact statements, tiered telemetry, and attribution/budgets.

- **Gartner (early 2025 webinar "I&O Leaders, Get Control of Your Observability Costs")**: observability cost rising **≥40%/year for 15 years**; **second-largest software line item in R&D after cloud**; most orgs spend **10–25% of infrastructure bill** on observability tools. (Note: ch23 says 20–30% of infra spend; ch25 "up to a third" — different framing; check book.)
- Real question: "did we buy the right capabilities, are we getting the right returns?" Mismatch: paying for strategic capability, operating as cost center, using like monitoring. Bad tool fit → outrageous bills; better results may cost less.
- Loops: **operational** (detect, respond, recover, prevent recurrence) vs **developer learning** (deploy, observe, learn, adjust). Different problems even if same tool (footnote: all data tools are fungible given infinite resources; you could debug prod in Excel).
- Ops focus → cost center governance (reduced spend, predictable overhead, coverage) — but cuts harm stability.
- **Firefighting trap**: ops loops are longest, lossiest, most expensive. "**If your goalie is making 50 saves a game, your defense is not working.**" (Footnote: if the goalie is the only one trying to score, you're really screwed.) Cuts → less data → blind spots → more risk, downtime, long-term cost; tool sprawl; degraded data quality. Diagnostic: **% of observability investment on fighting fires vs preventing them?**
- Dev loops → strategic investment governance (capability growth, learning speed, competitive advantage). Diagnostic: **does it produce organizational capabilities that affect business metrics?** Can't get learning outcomes with cost-center governance.
- **Activities vs learning**: chaos engineering without attribution = disruption; flags without validation = complexity; progressive delivery without detection = slower pipeline. Observability provides **attribution, validation, detection**. Diagnostic: for each practice, what feedback mechanism turns it into learning, and what % of the time is it used?
- **Indicators — operational investment working**: time to identify known causes decreasing; alert quality improving (fewer false positives, more actionable); escalation rates dropping; recovery faster. **Developer learning investment working**: engineers answer novel questions about prod; deploy frequency up and batch sizes down; more engineers debug independently; hypothesis-to-validation time shrinking; more issues found by engineers and fewer escalated by customers. Spend up with no indicator improvement → not working (not a communication problem; change tooling, instrumentation, org approach).
- **Advice**: (1) find **point of diminishing returns** per investment and cap; (2) **quantify visibility gaps** with **impact statements** (revenue loss + employee downtime, SLA penalties, churn, reputation); (3) **telemetry pipelines with tiered service**: "high" (critical path: revenue-generating, customer-facing, under active development → wide traces/canonical logs, high tail-based sample rate), "low" (stable, decoupled, non-customer-facing → end-to-end health checks + a synthetic or two), often a middle tier; control verbosity with **feature flags** (no redeploy); (4) **invest in attribution** ("observability for your observability"): tag requests with cost, line of code, normalized queries; tokens; **per-team observability budgets** → self-governance.
- Interview angles: how to respond to "cut observability spend"; diagnostic questions; leading indicators per loop; tiered telemetry design; impact statement; attribution and team budgets.

## Ch28 The Organizational Shift (read in full; Rick Clark, Global Head of Cloud Advisory at UST; no figures)
**Argument:** Many orgs have "legacy observability masquerading as modern observability". Diagnose with five evidence tests; understand the organisational immune response and why vendors, existing teams, and leadership resist; build a coalition (including legacy heroes); secure a mandate with real authority; execute a product-minded roadmap (one domain full depth, paved paths, rerun tests, expand deliberately); build an observability platform team (Wardley pioneers/settlers/town planners); break the vendor identity trap with open standards.

- Symptoms: war rooms, manual correlation, never deploy on Fridays, same three people, customers find bugs, mysteries become folklore, green dashboards. "The label does not change the capability."
- **Five tests**:
  1. **Ownership test**: "After you merge, how do you know it's working in prod?" Legacy: black hole; paged hours/days later or customer months later. Modern: live in minutes, notification link to canary, watch metrics. Measures energy/knowledge/creativity demanded to understand own change. "Pouring water into a leaky bucket."
  2. **Two-or-three people test**: do engineers use tools or ask the 2–3 experts? Modern: **60–80% of engineers investigate independently**. Experts = single points of failure, bottlenecks, burnout. "If your observability requires a firefighter, you do not have observability."
  3. **Mystery test**: "What's weird in prod that we just accept?" (midnight load spike, job fails sometimes, higher latency on Tuesdays). Modern: "batch analytics job triggers **40,000 DB queries** because the query plan changed". Search chat for "just does that sometimes"/"we never figured out"; count postmortems with unknown root cause; runbooks = "restart and hope". "Mysteries that persist are the shape of your blindness."
  4. **Arbitrary question test**: e.g. "all failed checkouts from mobile users in California on app v2.3.1 during lunch hour last week". Legacy: indexes? hours/days, manual logs, "we don't track that". Modern: **under 60 seconds**. "Monitoring answers questions you predicted. Observability answers questions you did not."
  5. **Deployment confidence test**: legacy weekly deploys, war rooms, "**read-only Fridays**", juniors can't deploy, **Change Advisory Boards**. Modern: multiple daily, automated. "They are not afraid of deploying. They are afraid of not knowing."
- Tests aren't a scorecard; they're evidence for the fight.
- **Organisational immune response**: committees to "evaluate options", pilots starved then declared failures, success criteria redefined, "everything's fine" reports. **Name it out loud** ("we're forming a committee to evaluate something we already know doesn't work").
- **Vendors**: auto-renewing contracts; sales comp on dashboards/storage/seats; roadmaps built on three pillars. Hard sells: AI feature magic bullet; "it's a tier problem" (premium tier); professional services; "you're using it wrong". Not evil or even wrong — misaligned (they win when you buy more; you win when you understand more).
- **Existing teams**: identity ("I'm the Splunk person") = **vendor-silo alignment**; headcount fears ("unified" sounds like fewer jobs); seen failed modernisations; skepticism earned. Be honest jobs change; expertise becomes portable; headcount shifts to non-heroic work; evidence they helped gather.
- **Leadership**: sunk cost of millions; "upgrade to enterprise tier" seems cheaper than admitting mistake; last consolidation added three more tools. Frame as **capability** not consolidation/cost; connect to bleeding outcomes: revenue lost to outages in critical flows, churn, senior salaries in war rooms, customer-found bugs, fear-slowed releases.
- **Coalition**: allies with skin in the game, credibility, willingness to spend political capital. Find pain: on-call engineers who are dispatchers to the same two seniors; SREs hand-correlating dashboards; security can't trace access; platform can't answer "what broke after that deploy?"; support can't explain; managers whose teams won't ship Fridays. **Honor the heroes** (3 a.m. scripts; know which dashboard lies; why a service restarts every Tuesday). **Rick's story**: excluded the principal network architect ("dinosaur"); he controlled **IP address allocation**; hours → weeks; went back, apologised, included him → obstacles disappeared. "One committed ally beats 10 passive supporters."
- **Build the case together**: run the five tests; collect stories (4-hour incident because only two people could query logs; support blind; bad deploy unknown for 3 days); measure burden (on-call escalations/week, war-room hours/month, % bugs found by customers).
- **Mandate**: new services instrumented the new way (not optional); new teams onboard to new standards; legacy migrates on a published timeline. **Sponsorship vs authority**: sponsorship without authority is theater. Right sponsor often whoever owns the pain (VP Eng explaining incident costs to the board; head of SRE owning MTTR; business leader asking "what happened?"); budget authority + patience into **year two**.
- **Pitch**: risk reduction ("we can't reliably debug prod, risk growing"), capability ("only three people can investigate"), burden ("best engineers spend **30%** of time in war rooms"). Don't frame as consolidation (bad reputation) or lead with cost savings (cut when budgets tighten). Open standards answer "another check leading nowhere". **AI forcing function**: AI code outpaces instrumentation; AI decisions hard to trace; ship faster, understand less = liability.
- **Roadmap**: mandate + product mindset → enthusiastic adoption, not compliance/sabotage. (1) **Start small, full depth**: one domain, willing team, neither most critical nor most neglected; wide events, request IDs across boundaries, cardinality; success = war-room questions answerable by a query; protect the team. (2) **Pave the path**: libraries, golden paths, correct defaults for 90%. (3) **Platform engineering principles**: customers = developers, 3 a.m. SREs, security, support, leadership; research needs; complaints are data; measure adoption/satisfaction; workarounds = product failure; **build as little custom software as possible** (OTel, buy commodity). (4) **Rerun the five tests at ~6 months**; business-adjacent metrics (time to resolve customer issues, war-room hours/incident, % bugs found internally). Celebrate milestones, don't declare victory. (5) **Expand deliberately**: new work built in; legacy migrates domain by domain; "stop the bleeding before healing wounds"; capability not project; budget shifts incrementally (**year one ~10%, year three ~40%**) = **strangler pattern**; let benefiting engineers evangelise. Done when war rooms stop, mysteries get solved, engineers ship on Fridays.
- **Observability team owns**: platform, instrumentation libraries/SDKs, telemetry standards, vendor relationships/tool selection, developer experience. Not instrumenting every service (bottleneck). **Capabilities**: pipeline integration (CI/CD, auto-injection), production expertise (felt 3 a.m. pain), developer experience, customer understanding (all audiences), standards & architecture (naming, propagation, cardinality guidelines), vendor/tool strategy (bias to buy + open standards), integration (connective tissue). Not 1:1 to titles; can be a small core + virtual team.
- **Simon Wardley: pioneers, settlers, town planners**: pioneers (greenfield, experiments), settlers (harden, libraries, docs, platforms), town planners (optimise, reduce cost, maintain legacy during migration). Don't force pioneers into town planning or vice versa.
- **Vendor identity trap**: OTel skills portable: "I'm the Splunk person" → "I'm a telemetry architect".
- **Don't promise "no one's job changes"**; promise "we need your expertise, and here is how".
- Conclusion: projects end, capabilities evolve; learn from production, not just survive it.
- Interview angles: the five tests; handling resistance; securing a mandate; first-domain selection; platform team responsibilities; Wardley archetypes; strangler-style budget shift; persuading leadership without cost/consolidation framing.

## Ch29 Build Versus Buy (Versus Open Source) (read in full in two passes; figs 29-1..29-3 are 2x2 matrices/platform diagram described in text)
**Argument:** Build vs buy is about which pain you tolerate (money vs time) and where engineering cycles go. Name biases. Observability isn't like other software (watches the watchers; needs independent HA). Use Rick Clark's 2x2 (business value × ubiquity → build/buy/should-not-exist/decide) or Peter Corless' OSS-aware version (create/adopt/acquire/avoid + commission). Count hidden costs of "free" software. Default: **buy the platform, build the integration layer** with an observability team.

- Context: observability spend second only to cloud. "Maintenance costs always dwarf the costs of building"; AI-generated code maintenance no cheaper (footnote).
- **DBA joke**: Oracle when you love your time and hate your money; MySQL when you hate your time and love your money (today: DuckDB vs Snowflake). "Hate money" path (engineering focus scarcest) vs "hate time" path (easier to justify $1M headcount than $100k tool). Mistake: treating internal builds as free because salaries are paid.
- **Biases**: authors' vendor bias (orgs underestimate build/run cost); engineering bias (Rick Clark, ex-Mastercard, VMware, Cisco, Pivotal: "engineers want to build just like surgeons want to cut"); sunk cost; **NIH** ("special snowflake"); fear of vendor death, lock-in, data gravity; migration fear. Have stakeholders put fears on the table.
- **Observability isn't like other software**: watches the watchers → higher reliability needs; running it on same cloud/region/stack means it degrades exactly when prod does. Vendor = HA + decoupled stack. If 98–99.5% availability is fine, self-hosted OSS can be cheaper.
- **Rick Clark 2×2** (Fig 29-1): x = **business value** (none → differentiator; = market share/revenue, not "importance" — e.g. secrets vault on a 448-CPU/24 TB RAM instance doesn't add revenue); y = **ubiquity** (commodity → bespoke). Two problem types: common to all businesses vs unique to your model (footnote: really three, incl. unique-but-shared-across-teams). Quadrants: **build** (high value + bespoke; e.g. Honeycomb's Retriever), **buy** (low value + commodity: service catalogs, identity, logging infra, observability platforms), **should not exist** (low value + bespoke; worst technical debt; e.g. **financial institution's custom threaded request handler for Apache HTTPD 1.3.x, 5x faster than stock; Apache 2.0 new module API/faster scheduler; developers gone; paid consultants >$10M when 1.3 support ended, after it became a regulatory compliance issue**), **decide** (high value + commodity; hard conversations; don't decide by managerial fiat; staff+ engineers with skin in the game).
- Sidebar: staff+ should build reputation for business-driven decisions; managers should promote on decision quality, not LOC. Engineers assume they'd get principal faster by spending **18 months and $20M** building observability from scratch than picking a vendor + integrations (1/4 the cost, half the time). Major driver of tech debt.
- **Decide-quadrant questions**: precise job to be done (rubric from stories/scenarios, not feature lists); how unique really (compare peers); smallest version (solve 80–90% with commercial + extensions); product management expertise available?; timeline; who supports it after builders leave? If you build because nothing quite fit, revisit in a year. Rule: closer to disk → prefer battle-tested; closer to UX → custom is normal (new DB/OS/filesystem needs very good reason; OTel wrapper library for frontend is normal).
- **Examples**: (1) **custom SLO/error budget tracking** → buy for ~90%; thin wrappers for 3–5 weird services (e.g. ML inference); internal SLO tools die without PM; "37 microservices? so does everyone"; footnote: most vendors can't do bidirectional SLO→requests ("killer capability" of unified tools). (2) **custom instrumentation wrapper** for React (autocapture user ID, session ID, flags; 3–4 helpers; ~**200 LOC**; ship in **two weeks**; frontend platform team owns) → **build** (UX layer). (3) **cost attribution/chargeback** → buy platform; build lightweight attribution script only with material spend + chargeback culture ("team X spent $4,500 this month"); political; needs an owner.
- **Generalised pattern**: infrastructure/storage → almost always buy; UX/workflow → often build (thin layers); intelligence/decision-making (>3 months to build) → build only with strong PM commitment.
- **Open source** = third option shifting where you pay: engineering time to evaluate/deploy/integrate, infra, maintenance/upgrades, opportunity cost, recruiting OSS-specific expertise. **Heidi Waterhouse: OSS is "free as in puppies, not free as in beer."** Source-available: can see but not modify/fix.
- **Peter Corless' framework** (Fig 29-2): quadrants **create** (bespoke + differentiator; IP: trade secret, trademark, patent, product, or open source it), **avoid** (= should not exist), **adopt** (commodity + low value: OSS/source-available agents, SDKs, catalogs, identity, logging, observability platforms; see/contribute code), **acquire** (commodity + differentiating value: COTS/SaaS, customise via plugins, can't change/see code), **commission** (straddles create/acquire: consultants, work for hire; you own the code — advantage and disadvantage).
- "There's always vibe coding" — excluded because no quality/accountability/governance; true cost was always operating/scaling/changing/monitoring code.
- **Build costs**: opportunity cost biggest; small team in a year vs vendor with hundreds/thousands of engineers and domain expertise.
- **"Free" ELK example**: vendor quote **~$80,000/month (~$1M/yr)**; "free" ELK actually: **dedicated hardware $80,000/month**, **three engineers at $250–300k each/yr**, recruiting **15–25% of annual earnings (~$75k each)**, hiring/training time → **>$2M/yr, more than twice** the commercial option. Calculate fully loaded engineer costs, infra, opportunity cost, maintenance.
- **Build benefits**: in-house expertise; deep customisation (can become liability); learn domain deeply (hit metric limits head-first); maybe cheaper/escape lock-in or become product/IP (be realistic); maybe only option (cheap basic monitoring nobody sells).
- **Build risks**: PM expertise rare (bad tool damages management trust); takes time (constructing office building before operating); never-ending support ("Google won't help when it breaks"); low adoption; common enterprise pattern: build v1, move on, abandon. Internal tools must be built like products (Abby Bangser; Jack Danger "Infrastructure Gravity & Domain Engineering").
- **Buy costs**: cost may not track value: Gartner customer +48%/yr for 15 years — "are you getting **35,800% (358x)** more value than in 2010?" Vendors need margin (if you pay less than cost, worry). Unfair: obscured TCO, stacked dimensions. Antipattern: **per-seat, per-host, per-service, per-query** metering; pay-as-you-go explodes. Team size, hosts, services, and especially **queries grow** with observability culture → avoid pricing that **penalises adoption and curiosity**; observability for support, product, design, security, marketing too. Demand cost estimates for today and 1–2 years out.
- **Nonfinancial cost: lock-in** via proprietary agents/formats (instrumentation is the most labour-intensive part). Use **native OTel** by default; vendor specifics via **OTel distros**/exporters. **Matthew Sanabria (Oxide)**: use OTel Collector not vendor agent; decorate and trim fields; model current and future costs; buffer for misconfigurations that explode bills; "do not trust anything not in writing". Some vendors disparage OTel in POCs to lock you in.
- **Buy benefits**: time to value (minutes/hours); streamlined UX (opinionated product vs OSS building blocks); offload maintenance; economies of scale; domain expertise. **Risks**: no in-house expertise; built for wide audiences (your features may not be priorities); no control (acquisition, funding, market pivot, outages).
- **Buy AND build** (Fig 29-3): vendor does heavy lifting; build friendly idiomatic libraries/tools/interfaces = platform model. **Observability team** (needed even when buying): write libraries/abstractions; standardise naming; handle upgrades; consult on instrumentation; manage vendors; decide on new tech; educate; training + sample code; integrate three-pillar sources; reduce friction and costs. Curate how outsourced work returns into the org (**Accelerate State of DevOps 2019**). Need vendor with strong **API** for programmatic config/query → "last-mile problem-solving".
- **Caveats**: (1) no large commercial offering at **monitoring price points** (free tiers don't scale — "first hit is free"); (2) **hyperscale** may justify building ("if you aren't building your own power grids, you're probably fine"; Meta builds power grids; usually driven by control not scale); (3) enterprise needs **tiers**: high-fidelity for critical/customer-facing/money-handling/active development; traces + tail sampling for stable customer-facing; basic metrics + synthetics for non-customer-facing; OSS for niche cases. "Lots of people believe their company is exceptional... completely ordinary."
- Conclusion: 10–15 years ago SaaS = hosted OSS; now commercial diverged. Default: buy platform, build integration layer. Build only if: truly unique requirements, massive scale, observability is your core business, or regulatory/security forbids vendors.
- Interview angles: apply the 2x2 to an observability component; hidden cost calculation (ELK example); OSS "free as in puppies"; pricing model red flags; avoiding lock-in with OTel distros; role of observability team when buying; tiered service model.

## Ch30 The Art and Science of Vendor Partnerships (read in full in two passes, 2026-11-27; no figures)
**Argument:** Buying observability is engineering ("vendor engineering"): wielding influence without authority across company lines. Map stakeholders, build credibility and trust internally, assume different goals with vendors but aim for reciprocity, encode the relationship in SLAs, scope the work and sponsor up front, adopt OTel, run a POC that load-tests your hardest problems, build champions, keep procurement moving, then migrate, decommission and plan the next transition.

- "Most software transformations fail"; those that succeed rely on trust and credibility as well as technical excellence and mandates. Skills are executive-level, durable post-AI, rare for ICs.
- **Charity's Mark Callaghan story (2013)**: ~30 people in a Facebook MPK 16 meeting room with Parse, Facebook and MongoDB (incl. MongoDB CEO/CTO). Parse on free MongoDB: crashes, MMAPv1 memory-mapped engine growing unbounded, RAIDing EBS volumes, consultants who knew less. Callaghan ("I always listen to operations"; reportedly E9 level invented for him) asked about roadmap/storage engine; lobbied for a **pluggable storage engine API**; got RocksDB team resources (MongoRocks), Parse as first customer; introduced Keith Bostic/**WiredTiger** (later acquired by MongoDB; default engine today). MongoRocks cut disk footprint **up to 90%** and enabled write-heavy workloads; averted "Mongogeddon". Vendor engineering = leveraging influence across company lines to move the industry forward.
- Vendor engineering vs buying software: buying takes money; vendor engineering takes technical depth, strategy, business priorities, change levers. Footnote: at very large enterprises this is principal/distinguished/chief architect work.
- **Before you start**: find local guidance (policy docs + local experts; apprentice yourself); understand your role = keep machinery moving through security, legal, architecture review; "assume nobody else cares enough"; **you're the sheepdog**.
- **Stakeholders**: **Engineering** (few are attached to tools; show tool solving their problems; find champions; "follow the pain"); **Management** (fit with direction, opportunity cost, adoption; control migration levers; written progress updates); **Finance** (cost, predictability, consolidation, ROI, time to value, contract terms; translate to outcomes; footnote: finance is fine with handwavy directional estimates); **IT/Ops and Security** (alignment, compliance, auth, deployment, support; observability data exposes customer data and internals; GDPR; compliance is flexible with right story and evidence for auditors; **"never accept a proxy no"** — footnote: it's usually security); **Procurement** (treat as friend; help them get a win; don't route around).
- **Communicating up**: you won't be in the room; put case in writing for sponsor; business outcomes; polish artifacts; **"surprises kill deals"**; footnote: list of major concerns with green checkboxes.
- **Credibility vs trust**: credibility = you assert something is true and it turns out true (be conservative in claims); trust = you say you have their interests at heart and actions prove it (extend yourself first). Alignment = solving your problem solves theirs; otherwise you're a petitioner. Trust is "grease in the machinery", lendable like capital. Build: help with their OKRs, grunt work, stick your neck out. Break: sitting on bad news; never sit on bad news or big scary numbers; be forthcoming especially if responsible; eliminate surprises.
- **Vendors**: opposite dynamic: assume you want different things; helpful only while you progress toward their sale; may mislead (incl. lying); "this is capitalism"; right baseline assumption. **Vendor trust coefficient**: honest when unflattering? lie or mislead by omission? FUD about competitors, "trap" questions? Do they help design a POC exercising hard cases, or offer to do the work in ways that hide weaknesses (test datasets "just as good")? "For every lie you catch, assume a hundred more." Double-check competitor claims.
- **Reciprocity principle**: be a customer worth retaining; vendor a service worth paying for; "both feel like high-fiving after negotiating". Don't gloat about vendor serving you at a loss. Opposite: "leave no money on the floor" pricing (charge to the point of pain). Some enterprises price-insensitive; care about trust and roadmap influence.
- **Influencing a vendor's roadmap**: important customer (logo/contract size); strategic alignment (cross-sell/co-marketing); **sweat equity**; technical credibility + personal relationships; organisational levers (**SLAs, OKRs, KPIs**). Vendors also need to influence customer roadmaps (a migration not on roadmap/OKRs never happens). Back channels fragile → codify.
- **SLAs encode the vendor–customer relationship** (as SLOs do for engineering–sales): formal legally binding contract on quality, availability, responsibilities, with metrics and remedies/penalties. Don't leave to vendor + procurement; get stakeholder buy-in; levers lasting after negotiators move on. More trust doesn't mean less SLA: "good fences make good neighbors".
- **Early-stage**: every successful transformation ends with a top-down mandate AND bottom-up groundswell. Get clear on **scope, success criteria, executive sponsor**. Three fictional scenarios: **Fort Pillars Financial (insurgency)**: Fortune 100, same three-pillars vendor 17 years at **$40M/yr**, **8,000+ engineers** without prod telemetry access, **MTTR 6–8 hours** hand-correlating; VP wants 2–3 product teams POC and ROI evidence ("make their eyes pop"). **Tool Sprawl Industries (consolidation mandate)**: 40+ tools, P0 took **14 hours** across five systems, spend **>$60M**, CEO/CTO/CFO directive, budget preapproved expecting **40–50% cost reduction**, **90 days**. **Agent Smith Systems (cutting edge)**: pre-IPO, early OTel, AI raised deploy rate **5–8x in 18 months**, vendor MCP times out/hallucinates metrics/can't do high cardinality; replace or augment undecided.
- **Scope**: too small misses the chance; too big founders on sunk cost, scope creep, turf. Goldilocks size set by air cover, evidence, and "populist ratio of anger to inertia".
- **Executive sponsor**: who can sign; who has budget authority (may differ); keep every management hop informed; model the decision-maker; silence ≠ agreement; "farm for dissent early and often".
- **Success criteria before starting**: biggest POC failure mode is never defining success; specific, measurable; functional requirements, architectural characteristics, budget; agreed by someone close to budget.
- **Coworkers perceive you as a threat**: threats to their **tools** (identity) and **turf**; they may sabotage, escalate, alert their vendor (even CEO-to-CEO). Seek counsel; keep extending a hand.
- **OTel decision**: adopt at instrumentation layer during evaluation ("let this be the last time you reinstrument"); a vendor discouraging OTel is locking you in (footnote: "more mature bespoke integrations" is by choice). AI + OTel cuts reinstrumentation burden.
- **POC**: a **load test of your hardest problems and representative production use cases**. Rubric comparing vendors (strong on 20% of what you care about → rule out). Instrument to see **each vendor at its best**, not lowest-common-denominator apples-to-apples. Real representative load in production; trust but verify. Elements: **description of your pain** (precipitating events), **definition of success** (outcomes), **required capabilities** (questions you ask/wish to ask; avoid solutions like "query language with joins"; list lossy/laggy workflows), **scope** (teams, workflows, datasets, out of scope). Timebound, resourced. Don't let vendor write requirements. Agree up front to proceed on data if tests pass.
- **Technical evaluation**: users vs gatekeepers; beware "poison pill" capabilities seeded by other vendors; define success by business use cases; test coexistence with old tool (**dual writes** via multiple OTel exporters).
- **Pricing at scale**: send a representative sample (one cluster) and extrapolate; **website prices are meaningless**; find a reference customer and ask what they pay and how many engineering cycles go to cost management (can be several salaries).
- **Champions**: solve the gnarliest problems (understaffed, woken nightly, principal engineer in every SEV0/SEV1); **brag list** of wins; praise publicly up the ladder.
- **Procurement momentum**: say something if blocked; "you are the sheepdog. Woof."
- **Migration**: handoffs (presales → post-sales; to platform/observability team) — stick around, explicit handoff. **Three steps**: de-risk with a nontrivial manageable example; bulk migrate (accept mess); iterate service by service. LLM tools cut months/years to weeks (sometimes days). Put milestones in OKRs/KPIs. **Don't import old tool config** (cruft); rebuild from business requirements. Present messy reality as linear progress.
- **Not done until you decommission**: last 10% hardest; publish deprecation timeline; only then full cost benefit. (Footnote: Parse burned unicorn piñatas when decommissioning the last Unicorn Ruby server.)
- **Plan the next transition**: write a recap; **requalify vendors on a regular cadence**; when cost approaches value reassess; parallel tests often yield discounts (footnote: cost evals feel like Groundhog Day). "Migration is an organisational muscle." Regulated environments require regular review anyway.
- Interview angles: how you'd run an observability vendor evaluation; POC design; stakeholder map; credibility vs trust; never accept a proxy no; SLAs; migration three steps; decommissioning.

## Ch31 Instrumentation for Observability Teams (read in full, 2026-11-27; by Hazel Weakly and Austin Parker; no figures)
**Argument:** An observability team's north star is to define and manage the organisation's shared telemetry language. OTel semantic conventions give the vocabulary and grammar; telemetry schemas treat telemetry like a versioned API contract; adoption comes from paved paths, not wiki pages; in regulated environments the same work has to produce evidence (compliance) and preserve isolation (security) while keeping correlation.

- Opening metaphor: language as fossil poetry (Emerson); culture shapes language. Code depreciates the moment it's written; needs gardening.
- Observability teams vary: a hat an SRE wears in small orgs; multiple teams in large ones; may report to IT or engineering; may look like vendor management. Authors' view: team should **own instrumentation widely** — instrumentation code/frameworks, pipeline config and management, alerting infrastructure, SLO tooling. You may not write the instrumentation, but you're judged by how much everyone else does.
- Prior attempts at universal telemetry semantics overfit a domain: .NET/Microsoft stack (vertical runtime–OS integration, generalised poorly); Java (until a React frontend or Swift app appears); *nix (learning cliff).
- **North star**: define and manage the constructed language of the org; archaeology of ossified internal terms plus a bridge to the industry's lingua franca; provide the framework ICs and leaders use to communicate intent and action.
- **Semantic conventions** = most valuable part of OTel for an observability team. Goal: telemetry as a trainable skill, portable across jobs. **Vocabulary** = names (`http.request.method`, `db.system`, `exception.type`, span name `GET <route>`). **Grammar** = how names are organised: dot-separated namespaces, families like `http.request.header.<key>`, requirement and maturity levels, stability. Two heuristics: namespaces go general → specific left to right; actors are client/server or producer/consumer. OTel defines many domains and ships instrumentation; **Weaver** lets you define your own.
- **Telemetry schemas**: bring API-contract practice (versioning, stable integration points) to telemetry: a textual description of what a service emits plus tooling for discovery, linting, creation, code generation. Not turnkey yet. Benefits: single source of truth near the code; discoverability (tools, audits, AI assistants reading it as context); **compile-time and runtime verification** (fail builds on unspecified attributes; pipelines drop mystery attributes); safe evolution (processors use schemas to normalise in flight).
- Schema-writing tips: **start from the why** (questions users ask; make common ones cheap); **define your namespace** (org-wide ids at a higher level: `acme.transaction.id` vs `acme.serviceName.transaction.id`; mixed identifiers produce wrong joins; AI pattern-matches hard and won't notice the difference); **abstract at actors/roles not protocols** (transports change); **DRY** (same key on different signals must mean the same thing; keep high-cardinality ids like transaction id off time series; put lower-cardinality `customer.region`/tier on metrics and layer signals, see ch7).
- **Sidebar, identifiers and security**: security thrives on isolation, compliance on evidence, observability on correlation. Use **consistent one-way hashes** of sensitive ids across the org to keep correlation without triggering compliance scope.
- Critique: schemas seem heavyweight for small orgs; really reflects misaligned incentives — dev teams see one service; observability team sees the firehose and is scored on cost. Direct cost accounting breeds resentment.
- **Tooling, migrations, paved paths**: not a wiki of best practices, not an agent + prebuilt dashboards. Anti-pattern: months of analysing dependencies, rolling out agents and dashboards as a fait accompli, which then gather dust. Spread a language like society does: education, dictionaries, rites, repetition → tools/frameworks, training, SDLC touchpoints, process.
- **Tools and frameworks**: (1) **Don't wrap the OTel API** (renaming methods = antipattern); extend it (decorators bundling a span start + metric updates) or build indirection (a single internal package re-exporting OTel plus existing instrumentation APIs, so many services migrate without breaking callers). (2) **Hide the right complexity**: SDK boilerplate becomes a one-liner in the service framework; file-based configuration is coming. **Context propagation** is what trips most teams: embed OTel in the RPC/service framework with a basic schema so adoption = upgrading an internal library.
- Backside: manage volume and quality with the Collector and Weaver. Prefer **custom extensions (a little Go) and your own distribution via OpenTelemetry Collector Builder (OCB)** over doing everything in config: more flexibility, lower resource use, smaller attack surface. Weaver in build/deploy pipelines to **live-check** emitted telemetry against registered schemas; also as a local hook.
- AI: capture preprod telemetry → Weaver → hand code + Weaver output to an agent to propose fixes (or open PRs if tests are strong). Regulated: Weaver in CI automates evidence for auditors that no sensitive data leaks.
- **Paved paths**: indifference is the default. **Dapper story**: adoption stalled until the team found where engineers already looked when paged and added **one link** from those monitoring graphs into Dapper; usage doubled then tripled almost overnight. Find where your engineers congregate (dashboards, alerts, wikis) and pave a path from there. "The right way and the fastest way should be the same way." Keep a brag book; stickers/t-shirts.
- **Make adoption safe**: Collector pipelines **dual-send** to cheap blob storage and the telemetry DB (esp. during migrations/sampling changes) to compare old vs new; rules (transform processor, schemas) dropping high-cardinality fields on metrics; default local-dev pipelines so devs see what's emitted; centrally managed pipeline config so it's clear why data was dropped. Sampling: biggest frustration is missing data you expected; dual-send as fallback; educate; simple rates first; start with "too much" and walk back.
- Role metaphor: mountain guide — not on the summit photo, but nobody dies.
- **Highly secure environments**: compliance ≈ the evidence you provide; security ≈ the isolation you guarantee; observability's superpower (correlation) cuts against both. Best practices become requirements; heavy burden of proof (end-to-end encryption, customer data handling, **FIPS 140-2** crypto in the Collector — all need evidence). Orgs only progress "mandatory" work and observability can't easily be mandated → design incentives so helping you makes others look good; frame as **facilitating compliance evidence collection**. Footnote: security projects are better funded — a way in.
- **Compliance tiers**: not every environment needs every control; provide a seamless way to graduate a service between tiers. A **12-month** path to production is normal in regulated industries. Don't hand devs a "production-ready" framework that costs months before any local data: "don't just shift tooling left; shift the value left".
- **Minimal capabilities**: **vendor management** (regulators assess your vendors; pay for what you ask); **encryption** (mTLS between every component, even within a trust boundary — a reason to prefer sockets for intra-service comms; plus at rest); **multilayer data analysis** (hardest: prove every byte sent anywhere meets requirements; data minimisation; locally safe data can be globally de-anonymising). All invisible work.
- **Valuable capabilities**: **chargeback** (staffing and visible value; cost in the language of the business); **schema control** (automatic checks for confidentiality levels; Weaver can decide between one observability deployment per application vs per environment); **data transport through proxies you control** (runtime scanning, policy agents, evidence of what goes to a third party); **tokenisation/anonymisation** (stops global correlation of locally safe data; enables side-channel correlation for sensitive payloads such as AI chat logs or DB queries; consistent one-way hashes); **authn/authz** (mTLS with short-lived credentials, attested identities, granular permissions). Plus non-technical: long-term support plans, migration operating models, blueprints, training courses, internal support SLAs, scanning/schema validation at dev, CI, deploy, runtime.
- Conclusion: the team's job is to enable, not claim, success. Signs: week-long conference bridges become days; SLOs used by directors and execs; compliance stops being a dirty word; observability language enters the engineering and business record.
- Interview angles: what should an observability/platform team own; how do you drive OTel adoption; wrap vs extend the API; telemetry schema as contract; cardinality guardrails in the pipeline; PII in telemetry (hashing/tokenisation); observability in regulated environments.

## Ch32 Where Do We Go From Here? (read in full, 2026-11-27; no figures)
**Argument:** The one prediction: the dev/ops line has to go, because AI changes the economics of code. Code stops being the precious record of intent and becomes a regenerable cache; the durable things are explicit commitments, specifications and evaluations, validated in production. Observability is how you start.

- Recap of the book's arc: control theory origins → instrumenting code → deep dives → decision-makers.
- **First-edition wish revisited**: better developer workflows in production. Verdict: still not there — developers still can't validate a diff they shipped or see its effect on a user subset; testing still means "correct in theory".
- **Prediction for 2e**: the dev/ops dividing line must be destroyed. Developers are builders of systems; the system is production. Not another mandate: core dev workflow must include instrumentation and production telemetry. "This time is different" because of AI.
- **Changing cost model**: the divide lasted because it made the change-vs-stability tension legible to org charts and budgets. AI attacks it: puts elite practices within reach of the median org; competitive pressure; nondeterminism (agentic workflows can only be validated by instrumenting and observing production, then porting into evals); above all the **economics of code production**.
- Historically code was scarce and expensive so we treasured it; trust lived implicitly in code that had run for years. Cost of software = cost of maintenance; readability was a proxy for maintainability. Small diffs were needed because behaviours were implicit and found by breaking them.
- **The most important parts were never specified**: the system = intersection of code, infrastructure, users, builders, data and time. Production code is the only record of intent, business needs and user expectations ("sedimentary layers"). To cut cost materially, **unbundle expectations from the artifact** and make them explicit elsewhere.
- **The great unbundling**: Chad Fowler's "Deletion Test" — what's lost if all source is deleted? Unknown required behaviour, unacceptable failures, invariants, how to tell a new version is correct, which bugs are deliberate fixes. Those are **evaluation problems, not code problems**. Bottleneck moved from generating to validating. Reframe: what must exist so code can be replaced safely? If you can delete and regenerate while keeping all commitments: **"code becomes cache"**; maintainability is a property of the system.
- **Human cost of compressed change**: disorientation/depression in some (engineers planning to retire), mania in others. Authors reject "AI is unprecedented / exponential forever": exponentials end in an S-curve or a crash; much pressure is marketing. Precedents: weaving → power loom; scribing → press/typewriter/word processor; pets → cattle. Becker (*More Everything Forever*): about **18x** harder now to sustain Moore's-law growth than in 1971. Software is language and logic — the low-hanging fruit, not a master plan.
- **Sysadmins went through this** (ENIAC ~80 years ago; code as sacred relic). Sysadmin craft devalued by automation; most adapted by writing code and building the systems that replaced their work.
- **From code to systems**: immutable infrastructure taught that in-place mutation creates drift. Ability to kill and regenerate is why we trust infra: **Honeycomb kills its oldest Kafka node by cron every Tuesday**. That we can't regenerate code the same way shows we don't understand it. Fowler: fear of "fresh code" is really fear of unobserved change; a system with stable contracts, strong evals, continuous monitoring and clear rollback tolerates fresh code; one without is dangerous even with ten-year-old code. Cheap code frees attention for architecture, coherence, UX.
- **Value must be backed by durability**: disposable software is for experiments; once it meets users, expectations and dependencies need continuity (nobody wants Slack's buttons rearranged daily). Dependencies need dependability. Migration ("crossing over", ch2) is still the hard part; zero-cost code doesn't change that. Specification + evaluation + testable commitments behind interfaces changes the cost structure.
- **Tools will come**: tools to extract commitments, keep intent, make architecture the versioned artifact don't exist yet. Understanding lags generation. Ideas exist, mostly from ops and QA: **behavioural tests, characterisation tests, capture/replay, traffic splitters** — observing and encoding what *is* happening. Start today: capture intent in instrumentation, follow it into production; can you, a coworker, an agent validate it there? Precision data (context + cardinality); build seams.
- Conclusion: transition from code-as-relic to code-as-cache will be messy; dev/ops divide stops making sense; "It starts with observability in production."
- Interview angles: "code is cache" and what it demands; validation as the bottleneck; how to make a system safe to regenerate; what replaces code review; testing in production.
